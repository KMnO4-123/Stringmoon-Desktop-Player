## 0. ⚠️ 先更正我自己此前文档里的两处错误

### 更正 ① `OPTIMIZE-v1-candidates.md` §5.1(d) 的无障碍建议是错的

我在那份文档里建议给虚拟列表**加** `aria-rowcount` / `aria-rowindex`。
**读了 `LibraryList.tsx` 才发现：这两个属性已经写上了，而且写在错的角色上。**

```tsx
// LibraryList.tsx:274 / :284（现状）
<div className="track-list" role="listbox" aria-label="曲库列表" aria-rowcount={visible.length}>
  <div role="option" aria-rowindex={index + 1} ...>
```

**WAI-ARIA 1.2 对 `aria-rowcount` 的规定**（[W3C WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)）：

> **Used in Roles: `table`** ｜ **Inherits into Roles: `grid`, `treegrid`**

**`listbox` 不在其中，`option` 也不是 `row`。** 这两个属性在这份标记里**不生效**。

**虚拟化 `listbox` 的正确机制是另一对**（[MDN `aria-setsize`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-setsize)，原文举的就是这个场景）：

> In a `listbox`, when the complete set of available options is **not present in the DOM due to dynamic loading on scroll**,
> both `aria-setsize` and `aria-posinset` can be set on each `option`.

**→ 修正是"换"，不是"加"**：`aria-rowcount` → 去掉；`aria-rowindex` → `aria-posinset`；
容器上加 `aria-setsize={visible.length}`（或每个 option 上都带）。

**代价**：**如果只写了 `aria-rowindex`，读屏可能跳行甚至停摆**（APG 原文警告：*"could cause screen reader table reading functions to skip rows or simply stop functioning"*）。
**现在这份标记的净效果是：写了两个无效属性，且缺了两个有效属性。** 成本极小，收益确定。

### 更正 ② `FIX-preventClip-peak-basis.md` 让应用自己算 dB→线性，是多余的

我在那份文档里写：应用侧必须 `Math.pow(10, truePeakDb / 20)`。
**但引擎已经把线性值算好并返回了**（`app.cpp:862` 与 `:968`）：

```cpp
j.set("peakLinear", truePeakLinear(r.truePeakDb));
// 注释原文：Linear as well as dB: the preventClip cap works in amplitude,
// and making every caller do the conversion is how one of them gets it wrong.
```

**→ 正确做法是直接传 `peakLinear`**，而不是在 TS 里再推一遍。
**理由与引擎作者写的一致**：**同一个公式有两份实现，早晚会漂移** —— 这正是我方 `computeStaticGainDb` 那条注释在防的事。

**这两条我都已核实（读的是本仓代码与 W3C/MDN 一手规范），不是推断。**

## 2. 主项 A —— 把"听得出吗"变成**可判决**的

> 这是整份文档里唯一一件**不解开就会一直在猜**的事：
> **你报告"糊、声场不够清晰、分离度不足"，而引擎证明了解码逐位正确、DSP 出厂默认逐样本恒等。**
> 于是只剩三种可能：**(a) 别的播放器加了东西 (b) 文件本身是升频/转码来的 (c) 差异不在软件层**。
> **A1 判决 (a) 和"我方两个配置之间有没有区别"；A2 判决 (b)。**

### 2.1 ⭐⭐ A1「对照」—— 两次减法，而不是一次盲听

**先纠正一个常见误解**：盲听回答的是"**听得出吗**"，
它**不回答**"**两者到底有没有区别**"。**前者是统计问题，后者是测量问题。两者都要做，且顺序不能反。**

**⭐ 而第 3 + 4 + 8 条事实让"测量"这一步变得非常便宜**：

```
引擎已能离线渲染文件（事实 3，--probe-resample 的骨架）
引擎已能离线测响度与真峰值（事实 4，analyze_loudness）
DspChain::process() 是公开、零分配、RT 安全的（事实 8）
────────────────────────────────────────────────
→ 把一首歌分别用配置 A / 配置 B 离线渲染成两个 WAV，然后逐样本相减
```

**这就是数字域 Null Test：不需要回环、不需要 DAC、不受独占限制、精度是"每一位"。**
回环门禁说的"独占录不到"在这条路上**根本不构成问题** —— 因为**信号从没离开过程序**。

#### ⭐ 改动点小到可以精确写出来（已读 `probe_resample.cpp` 全文）

现有骨架已经是**"解码 → 拉取 planer float 块 → 写 WAV"**：

```cpp
const uint64_t got = resampler.pull(planes.data(), kChunk);   // L108
// ... 写出 ...
```

**A1 需要的唯一改动**：在 `pull` 与写出**之间**插入 DSP 链：

```cpp
const uint64_t got = resampler.pull(planes.data(), kChunk);
if (got) chain.process(planes.data(), channels, static_cast<int>(got));   // ← 只加这一行
```

`DspChain::process()` 是**公开、零分配、RT 安全**的（事实 8），
**所以"用引擎真实的 DSP 渲染离线文件"不需要新写 DSP，只需要接线。**

#### ⚠️ 两个会让整个测试失效的陷阱（必须写进实现）

**陷阱 ①：不要渲染成 16-bit 再相减 —— 会被 dither 淹没**

现有写出路径在**输出位深低于源位深时应用 TPDF dither**（`dsp.hpp:191-257` 是这条规则的定义处）。
**后果**：把两遍渲染都写成 16-bit，**两次的 dither 噪声不同 → 相减得到的是噪声，不是差异**。
**更坏的是它看起来像"有差异"**，于是你会去追一个不存在的区别。

**→ 要求**：**比较必须在 float32 域做**（写 float32 WAV，或直接内存相减）。
**且禁止在对照路径上启用任何输出量化。**

**⚠️ 附带一条**：现有 `--probe-resample` 的 `bits=32` **并不是 float32** ——
它对非 16 位一律用 `full = 8388607.0` 缩放（`probe_resample.cpp:115`），
**即"24 位数据装进 32 位容器"**。**照抄它做 A1 会悄悄丢掉低 8 位。**

**陷阱 ②：A 与 A 相减必须真的是全零**

见验收 V1。**如果同一配置渲染两次都不全零，那说明渲染路径本身不确定**
（线程、dither、重采样器状态、未重置的滤波器状态任一都可能），
**那么任何"有差异"的结论都不能信。**

**→ 这正好是我方 `bitPerfect` 那条纪律的离线版**：**先证明尺子是直的，再量东西。**

| | ① **离线相减**（测量） | ② **电平匹配盲听**（统计） |
|---|---|---|
| 回答 | **两者到底一样不一样** | **这个差别你听得出来吗** |
| 依赖 | **零硬件依赖**，纯离线 | 需要能出声 |
| 精度 | **逐样本、逐位** | 统计（n 轮二选一） |
| 何时用 | 任何两个**我方配置**之间 | 任何"我觉得这个更好"的场合 |

**⚠️ ② 有一个硬约束（不能假装它不存在）**：

| 要对比的东西 | 能否边放边切 |
|---|---|
| **DSP 层**（EQ / 中侧 / 交叉馈送 / 预增益） | ✅ **能** —— 引擎已支持热改参数，且 EQ 有 30 ms 交叉淡化 |
| **设备层**（独占 vs 共享 / 重采样率 / 输出位深） | ❌ **不能** —— 换模式要重开设备，必然有中断 |

**→ 设备层只能"同段落、多轮重放"来比**，而这是 ① 更该发力的地方。

#### 最低要求（缺一条，这个功能就是自欺）

| # | 要求 | 为什么 |
|---|---|---|
| **1** | ⭐ **电平必须先匹配再切**，容差 **±0.1 dB** | **"更响"会被当成"更好"** —— 这是盲听最常见的假结论 |
| **2** | **匹配不上就拒绝跑，并说清为什么** | 做不到就说做不到；**跑一个没匹配的对照，比不跑更坏** |
| **3** | **统计只报"纯猜中概率"，不报"结论"** | n=8 的 7/8 是 p≈0.035，n=16 的 10/16 是 p≈0.23 —— **只报 p，不替你下结论** |
| **4** | 切换**不允许有提示音/闪动/任何提示** | 有提示就等于告诉了你哪边是哪边 |
| **5** | **结果可保存成一条记录**（配置对 + 轮数 + p） | 否则下次还要重新怀疑一遍 |
| **6** | ⭐ **轮数事先定死，中途不能改、不能重置** | foobar2000 作者自己的 v2.0 说明原文：*"Trial count is configured in advance and **not influenced by trial progress**"*、*"Trial can no longer be reset while in progress"* —— **事后挑轮数等于自己骗自己** |

**⭐ 而且有一条** foobar2000 **官方文档里【没有】的，正好是我方可以做得更好的地方**：

> **它的电平匹配要靠用户自己先跑 ReplayGain** —— 官方组件页、版本历史、KB **三处都没有自动匹配**的记载。
> **→ 而"先匹配再切"正是我方 §2.1 要求 1。这一条是真实的差异化，不是自我吹嘘。**

⚠️ 但**不要说它"没有"电平匹配** —— 正确表述是：「**它的官方文档里没有记载**」。**"文档没写"不等于"不存在"。**

**⚠️ 诚实边界**：**盲听只测"你这个人此刻能不能分辨"**。
它**不能**证明"两个配置客观不同"（那是①），也**不能**外推到别人、别的曲子、别的耳机。

#### 为什么它值得做（而不是花哨）

- ⭐ **它把音效链从"调着玩"变成"可判决的"** —— 你调中侧宽度/交叉馈送**到底有没有用**，这里给答案

### 2.2 ⭐⭐ A2 来源核验 —— **先排除"文件本身就是转码来的"**

**这一条的证据在地板里，而且引擎作者已经替你把话写清楚了**（`probe_spectrum.cpp:1-10`）：

> A FLAC that was transcoded from a lossy file is indistinguishable by container:
> it is a real FLAC, it **decodes bit-exactly**, **`sourceExact` is honestly true**,
> **and it still sounds muddy with a flat soundstage** — because everything above the
> encoder's cutoff is gone and the coder's own artefacts are baked in.

**注意这句话的形状**：**"解码逐位正确"与"听起来糊"完全不矛盾** —— 因为**信息在编码前就已经丢了**。
**这正好解释了为什么我方所有数字检查都通过、而你的耳朵仍然不满意。**

而且这本库的**先验概率不低**：**91 首里只有 1 首有 `album` 标签** —— 一个标签都填不全的来源，出现转码资源的可能性是真实存在的。

**做法**：把 `--probe-spectrum` 的逻辑产品化，加一条 `analyze_spectrum` 命令（形态照抄 `analyze_loudness` 的异步 + 进度事件 + 缓存），结果落成每首一条。

| 项 | 内容 |
|---|---|
| 判据（引擎已有） | 取中段 24 个窗平均，找**仍在携带能量的最高频率**，与自身 Nyquist 比 |
| `~22.0 kHz`（44.1k 文件） | **全频带存在** |
| `≤20 kHz` 且边缘陡峭 | **与有损源一致** |
| 结果措辞 | ⭐ **"停在与有损源一致的位置"，不是"这是假 FLAC"** |
| ⚠️ 缓存键 | **必须含 `size` + `mtime`**（照抄响度缓存的 `CacheEntry`） |

**⚠️ 这条功能唯一的风险是"过度解读"，所以措辞必须由引擎的原文决定**（`probe_spectrum.cpp:156-157`）：

> a genuinely band-limited recording (old analogue masters, some classical releases)
> also stops early, and this check **cannot tell those apart**. **It is a triage tool.**

**→ 界面永远显示为"证据"而不是"判决"，并且把上面那句原话作为可展开的说明。**
这不是啰嗦 —— **这正是我方"界面不能声称一件没发生的事"的落地**。

**为什么它独特**：**主流播放器都不告诉你这件事** —— 它们把你听到的锅留给你自己猜（换耳机、换播放器、换解码器）。**这一条是本项目护城河的直接延长线。**

**成本**：引擎小-中（逻辑已存在，加命令 + 异步 + 缓存）｜ 应用小（一个徽标 + 展开说明）

## 3. 主项 B —— 把"声场"变成**可测量**的

> 你的原话是"**声场不够清晰、分离度不足**"。这三个字**目前没有任何数字对应它**，
> 所以现在只能靠换配置然后凭印象说"好像好一点"。**下面两条把它变成数字。**

### 3.1 ⭐ B1 相关度（单声道相容性 / 宽度）—— **一个 float，直击你的抱怨**

**为什么是它，而不是更多表**：**相关度就是"左右声道有多像"的可测量定义**。
它正是**中侧处理、交叉馈送、宽度**这些已经存在于引擎里的控制**改变了的东西**。

```
correlation = Σ(L·R) / √(Σ L² · Σ R²)      // 窗口内，-1 … +1
```

| 读数 | 含义 | 界面怎么标 |
|---|---|---|
| **≈ +1** | 两声道几乎相同 = **窄/近单声道** | "接近单声道" |
| **≈ 0** | 两声道大体独立 = **宽** | "宽 · 单声道下会损失内容" |
| **负值** | **存在相位问题** —— 单声道相加会抵消 | ⚠️ **琥珀标注，并说明"单声道播放会丢失内容"** |

**SOS 对这一点的表述**（[Sound On Sound](https://www.soundonsound.com/sound-advice/q-what-are-my-phase-correlation-meters-telling-me)、及 r/audioengineering 讨论）：

> any steady reading in the negative half indicates **a reduced degree of mono-compatibility**:
> something will get lost (or attenuated) when you listen in mono

#### ⛔ 先说清它**不能**干什么（否则这条会被误读）

**所有表（相关度 / LUFS / DR）量的都是「节目」，不是「通路」。** ——
**同一个信号，无论播放器是位精确还是在重采样，这些表的读数完全一样。**

**所以：相关度表【不能】解释你的"糊"。**
它是**内容**的属性，不是**链路**的属性。**任何指望用表来判决保真的想法都是错的。**

**→ 判决保真只有一条路：做减法（§2.1）。** 这也是本轮调研最重要的结论。

**那它凭什么值得做？** 因为**它能量出"我方 DSP 到底做了什么"** ——
你调 `midGainDb` / `sideGainDb` / `stereoWidth` / 交叉馈送**时**，
相关度是**唯一能立刻告诉你"这一下改变了多少"的数字**，而且**它就在同一份 meter 数据里**。
**它是"调音台上的表"，不是"示波器上的真相"。**

**⚠️ 三条纪律（不做成"声场 3D"式的营销）**：

| # | 纪律 |
|---|---|
| **1** | ⭐ **不说"更宽=更好"** —— 相关度**没有好坏方向**，只有"是什么" |
| **2** | **不叫"声场/环绕/3D"** —— 叫「**立体声相关**」或「**单声道相容性**」 |
| **3** | ⭐ **与 A1 并排用**：调中侧宽度时**看着这个数**再做盲听，而不是只看数或只听耳朵 |
| **4** | ⭐ **必须印出公式** —— 否则它变成又一个"各家自定义的立体声宽度"（见下） |

**⚠️ 一条别人踩过的坑**：**"立体声宽度"这个标量没有标准定义，各厂商算法都不同。**
**→ 我方要么印公式，要么不显示宽度数字。** 相关度本身有标准定义，**这是选它而不选"宽度"的另一个理由。**

#### ⭐ 调研带回的两条有用参照（都不是抄，是校准）

| 项 | 参照 | 我方怎么用 |
|---|---|---|
| **可读带宽** | FFmpeg `f_ebur128.c` 的图形着色**只看目标 ±1 LU 那条带** | 相关度同样**只标"接近 ±1 / 接近 0 / 负"三档**，不做连续色带 |
| ⭐ **位表（bit meter）** | `foo_vis_spectrum_analyzer`（**MIT**）有一个 **Bit Meter**：显示**哪些位平面真的在跳** | ⭐ **如果低位全是 0，说明某处被截断了** —— 这是**最便宜且最诚实**的"信号没被动过"显示，**且它确实与 A1 互补** |

**→ 位表值得单独列进候选**：它**不量节目、只量位**，所以它**不会**犯本节开头那个错。

**⭐ 为什么现在做最便宜**：**CR-015 已接受但引擎尚未实现**（事实 7）——
**加一个字段是往一条还没铺好的管道里多穿一根线**，等实现完再加要多改一轮。

**成本**：引擎**极小**（meter tap 里多一个累加，控制线程算一次除法）｜ 应用小

### 3.2 ⭐ B2 「三组数」与信号路径留痕 —— **补齐缺口，不是重做**

`OPTIMIZE-v1-candidates.md` §3.6/§5.1 已提出，C2 的 6 段也已存在。
**这里只写仍然缺的那一块**：

| 缺的 | 具体 |
|---|---|
| ⭐ **三组数没有并排出现** | 「**文件** 96k/24」·「**引擎内部** 96k/float32」·「**输出** 96k/32(24有效)」—— **任一级不等就标出来** |
| ⭐ **`preventClip` 用的是哪种峰值没有出处** | 用 §0 更正② 的做法传 `peakLinear`，**并在信号路径上写明"真峰值"** |
| **任何 DSP 哪怕 0 dB 也留痕** | 与 Roon 一致；我方 `degradeReason` 纪律天然支持 |

**这三条的收益**：**别人在这件事上翻车 5 次**（见 candidates §3.6 的五条一手反例），
而**第 1 条正是"信号路径歧义"的根因** —— 不区分这三组，就会写出 *"the signal path is lossless (bit perfect)"* 这种真假掺半的话。

#### ⭐ 从 Roon 官方文档带回的四条（都是**可核实的**，不是印象）

Roon 的 Signal Path 是这门做法的标杆，它的**语义是公开写明的**（[help.roonlabs.com](https://help.roonlabs.com/portal/en/kb/articles/signal-path)）：

| # | Roon 的做法（原文） | 我方怎么用 |
|---|---|---|
| **1** | ⭐ **它明说自己是"预测"而不是"证明"** —— *"Roon uses four colors to **predict** the sound quality"* | ⭐ **这个姿态比任何颜色都重要**。我方有 `pcmPassthrough`/`outputPerfect`/`sourceExact` 三个**可核对**的字段 —— **比我"预测"更硬，所以更该少说形容词** |
| **2** | ⭐ **它自己划了边界**：*"it's **impossible for us to identify every processing step**… particularly after we've **handed it off to a hardware device**"* | ⭐ **这句话应当被我方采纳，而且我方还多知道一件事**：引擎能证明到**设备端点为止**，**端点之后（DAC 内部、模拟、耳放）我方一律不声称** —— 这正是 §6 里"糊可能不在软件层"那条的正式表述 |
| **3** | **削波指示：单个样本即触发，且只"瞬间"变红** | 与 `preventClip` 同族；⚠️ 但**它要求先开 Headroom Management 才生效**，且 0 dB 时**明确声明样本不被改动** —— 这个"**0 dB 即真旁路**"的语义与我方 `isPassthroughConfig` **完全一致** |
| **4** | **颜色键在"处理量"** —— *"The color is determined by how much processing is involved"* | 与 C2 的 6 段几何**同构**；我方**零颜色依赖**，这部分已经更强 |

**⚠️ 一条要避开的**：`JRiver` 的 "Direct" **允许音量改变**（它自己的截图就叫 *"Direct playback (with volume)"*）。
**→ 我方不能学这个词。** "直通"必须严格等于**样本未被改动**，否则就是我方一直在防的那种含糊。

**→ 顺带一条已核实的 Windows 事实**（Audirvana 官方技术页）：
**Windows 上只要拿到 WASAPI 独占（或 KS），格式即被尊重，不需要 macOS 那种"整数模式"开关。**
**所以"整数直通"这件事在我方平台上不是一个开关问题** —— 省掉一类无效讨论。

## 4. 主项 C —— 记忆与克制

> **这一节的共同主题是情绪价值，但方向是反的**：
> **不是让 App 更"懂你"（那是讨好），而是让 App 更"如实"（那才值得信）。**

### 4.1 ⭐ C1 聆听记录 —— 用**会话日志**，不是播放次数

**⚠️ 先说要避免的东西**（有依据的反对）：

| 别做 | 为什么 |
|---|---|
| **只存一个 `playcount`** | 它**丢掉了唯一重要的信息**：你是听完了，还是 6 秒就跳过。**同样存储成本，会话日志严格更有信息量** |
| **`score` / `autoRating`** | Clementine 算了、存了、导出到 MPRIS，**默认构建里没有任何东西消费它** |
| **`skipcount` 单个计数** | "4 秒跳过"和"95% 处跳过"**是相反的含义，被压成了一个数** |
| **从别的服务导入播放次数** | 91 首的库，**听几周就自己长出来了** |

**存什么**（每段聆听一条）：

```
trackId · startedAt · endedAt · startOffsetMs · endOffsetMs · endReason
endReason ∈ { completed | skipped | stopped | error }
```

**推出的两个事实**（都来自同一条日志）：

| 事实 | 怎么算 | 值在哪 |
|---|---|---|
| **听完率** | `(end - start) / duration` | 只报这个，**不报"评分"** |
| ⭐ **「没听完过」** | 所有会话里 `max(完成比) < 阈值` | **"你从来没把这首听完"** —— 诚实，且**比任何推荐算法都更了解你** |

**⭐ 完成判据照抄一手依据**（Last.fm 官方 scrobble 规范，原文）：

> The track must be longer than **30 seconds**. And the track has been played for at least
> **half its duration, or for 4 minutes (whichever occurs earlier.)**

**Clementine 的可读实现**（GPL-3.0 → **只借模式**）：`qBound(31s, length/2, 240s)`，
seek 之后重算为 `qBound(S+31s, S+length/2, S+240s)`；
并且它**刻意把"计次"和"上报"两个阈值分开**，源码注释给的理由是
*"someone's preferences for tracking play counts are more relaxed than that of scrobbling"*。

**⚠️ 三条自律（这就是"情绪价值"的正确形态）**：

| # | 自律 |
|---|---|
| **1** | ⭐ **身份用内容派生，不用路径/修改时间** —— 否则改个标签就丢历史（foobar2000 在 3.1.3–3.1.5 连修三次，就是这个病） |
| **2** | ⭐ **绝不用它自动跳歌、自动推荐、自动"为你播放"** —— **记录是为了如实，不是为了替你做主** |
| **3** | **可看、可清空、可关** —— 本地单文件，不上传，不进日志 |

**为什么它是"独特"的**：**主流播放器把播放历史做成了推荐算法的燃料**（为了留住你）。
**这里它是镜子，不是钩子。** 这是唯一一个**方向完全相反**、因而无法被抄走的设计。

**成本**：**小**（一个 JSON + 主进程写入）｜ 无 CR

### 4.2 ⭐ C2 恢复原状 —— **恢复但暂停**

**现状（已核实）**：应用侧**没有保存播放位置**，退出即失忆。

**正确做法照抄两个独立实现**（都是 GPL，**只借模式**）：

| 实现 | 做法 |
|---|---|
| **Strawberry** | 只存三项：`playback_state`·`playback_playlist`·`playback_position`；**恢复前先校验歌单身份一致**，**恢复成功后立刻把存档清空**（源码注释：*"so we don't resume again from the same position"*） |
| **MPD** | `state_file` + `state_file_interval`（默认 **120 秒**，*"after each state change"*）；且 `restore_paused` 可配 |

**⭐ 三条硬性**：

| # | 要求 | 依据 |
|---|---|---|
| **1** | ⭐ **恢复成"暂停在你离开的那一秒"，必须你按播放才出声** | **不是偷懒，是礼貌** —— 用户没要求出声。MPD 默认 `restore_paused no`（会直接播），**我方选另一条** |
| **2** | ⭐ **按"曲目身份 + 偏移"恢复，绝不按行号** | MPD 协议原文：position *"is a 0-based index. It is unstable by design… a client can never be sure what song is behind a given index."* |
| **3** | **落盘要防抖**（照 MPD 的 120 秒），**而不是每秒写** | 30 Hz 的 position 事件**不能**直接触发写盘 |

**成本**：**小**（主进程写一个文件 + 启动读一次）

### 4.3 C3 停止于当前曲末 + 睡眠 —— **让"停"成为一等操作**

**为什么需要**：**自动续播是默认行为，而"听完这首就停"目前做不到** —— 只能手动暂停，然后忘了。

**⚠️ 这里有一个真实的取舍，必须写清楚**（来自 Strawberry 源码，不是我的意见）：

> `TrackAboutToEnd()` **提前预载下一首**（这样做 gapless）。
> **诚实的后果：gapless 既是连贯性的胜利，也是"克制"的损失** ——
> 它**抹掉了听众用来决定"要不要停"的那段安静**。

**→ 裁决**：**两者都留，但把取舍摆到台面上**：

| 做法 | 说明 |
|---|---|
| 「**这一首放完就停**」 | 与 gapless **不冲突**：预载照做，**到边界时不接** |
| **睡眠定时器** | 「N 分钟后淡出停止」/「当前专辑放完」—— 淡变能力已有，**复用** |
| ⭐ **不做的** | **不做**"只听前 30 秒"式的自动跳段（Strawberry 的 `RepeatMode::Scan`）、**不做**自动跳过你不喜欢的歌（Clementine 的 `Ban()` 会直接帮你切歌）——**那是播放器替听众决定一首歌值多久** |

**电源这一条要按规范做**（一手依据）：

| 平台机制 | 用哪个 |
|---|---|
| Electron `powerSaveBlocker` | ⭐ **`prevent-app-suspension`**（官方文档把 *"playing audio"* 列为适用场景） |
| ❌ 不用 | `prevent-display-sleep`（那是视频的场景，且**优先级更高会压过前者**）|
| MSDN `SetThreadExecutionState` 原文 | *"cannot be used to prevent the user from putting the computer to sleep. Applications should respect that the user expects a certain behavior when they close the lid"* |

**→ 界面如实说**：**"播放时会阻止系统挂起，但不会阻止你合盖/关屏。"** 说得出做不到的事，不如说做不到。

**成本**：小

## 5. 横切 —— 可达性不是加分项，**是专业度的一部分**

### 5.1 ⭐ D1 每个滑块配一个数字输入（一次改动，两个收益）

**依据（WCAG 2.2 SC 2.5.7 Dragging Movements，Level AA，原文）**：

> All functionality that uses a **dragging movement** for operation can be achieved by a
> **single pointer without dragging**… *"a text input can be an acceptable single-pointer
> alternative to dragging. For example, an input beside a slider could allow any user to
> enter a precise value for the slider."*

**它同时满足你说的"专业控制"**：**能精确输入、能小步进、能一键回到中性**。

**ARIA 契约照 APG 的 spinbutton 模式**（原文）：`role="spinbutton"`、`aria-valuenow/min/max`、
`aria-valuetext`（当原始数字不好读时）、越界时 `aria-invalid="true"`；
键盘**↑/↓ 一小步；PageUp/PageDown 一大步；Home → 最小；End → 最大**。

**适用面（现有控件）**：音量 · 进度 · EQ 十段的增益 · 中侧/宽度 · 交叉馈送参数 · 歌词偏移。

**⚠️ 一条容易做错的**：**"回到中性"必须区分"从来没动过"与"动完又调回来了"**。
HTML 标准的 `dirty value flag` 就是这个概念的正式定义（*"If it is true, the default value is ignored"*）——
**不自己建模这个标志，"重置"就无法说实话**。

### 5.2 D2 修 §0 更正① 的无障碍缺陷

见 §0。**换属性，不是加属性**，并补一条断言：
**滚动到底后，可见行的 `aria-posinset` 必须连续且严格递增，且 `aria-setsize` 恒等于总数。**

### 5.3 ⚠️ 一条不做假承诺的

**Electron 文档原文**：`app.setAccessibilitySupportEnabled()` ——
*"the user's system assistive utilities have priority over this setting and will override it."*

**→ 所以不写"屏幕阅读器支持：已开启"**（那是在声称一个你控制不了的状态）。
要写就写「**请求启用辅助功能**」。

## 6. ⚠️ 明确**不做**的（附理由，防止以后反复讨论）

| 不做 | 理由 |
|---|---|
| **推荐系统 / 每日推荐 / "为你播放"** | 91 首自用库，**推荐的信息量趋近于零**，而它会**把你自己的曲库变成它的算法** |
| **"最常听"榜单 / 年度总结** | 会话日志已经在本地了，**要看你随时能看**，不需要做成推送 |
| **社交/分享/账号/云同步** | 已裁定不做 |
| **HRTF / 环绕 / 聆听房间** | `SPEC §3.8 / §6.3` 明确 Won't，且**与听清原音相冲** |
| **ABX 的完整仪式感**（隐藏参考、编码切换） | 只保留"电平匹配 + 盲切 + 报 p"，其余是仪式 |
| **"更宽=更好"式的声场营销** | 相关度没有好坏方向，**说了就是编** |
| **给播放历史做"智能"用途** | 见 C1 自律 2 |
| **`role="grid"` 重写曲库列表** | APG 明确偏好原生语义；且用 grid 就要**自己承担整套键盘契约 + 焦点恢复**，成本远超收益 |
| **"Hi-Res" 这个词** | JAS 注册商标（第5654058号），**使用需授权**，且听感项"各社自行规定"= 没有标准。改用「96/24 及以上」 |
| **任何形式的听力健康说教** | 引擎知道的是**电平**，不是**你的听力**；没有因果依据的劝导就是唠叨 |

>
> **① 动态范围 DR 表** —— 调研发现**市面上有两个互相矛盾、都叫"DR"的定义**

> （与 §3.1 开头的坑同一个错误）。**频谱是好看的，但它不是证据。**

**前 4 项全部不阻塞、不互相依赖，且 1–3 今天就能开工。**

## 8. 验收（可断言，不是"看着对"）

| # | 验收 | 通过标准 |
|---|---|---|
| **V1** | **A1① 相减自证** | **A 与 A 相减必须逐位全零**（同一配置渲染两次）。**这条不通过，后面所有减法结论都无效** |
| **V1b** | ⭐ **对照路径不得有量化/dither** | 相减必须在 **float32** 域；**对照渲染里出现任何输出位深量化即视为失败**（否则 dither 噪声会被误读成"有差异"） |
| **V2** | **A1① 灵敏度对照** | 人为改 **±0.1 dB** 必须能被相减检出 —— **证明这个测试测得出东西**，而不是永远返回零 |
| **V3** | **A1② 电平匹配** | 两配置的输出响度差 **≤0.1 dB** 才允许切换；匹配不上时**必须拒绝并给出原因** |
| **V4** | **A2 措辞** | 结果文案**不出现"假/伪/转码"**等判决词，且"triage"的限定条件**可展开读到** |
| **V5** | **B1 相关度** | 单声道信号 → **+1.0**；反相 → **-1.0**；两声道独立噪声 → **≈0** |
| **V6** | **C1 完成判定** | `qBound(31s, len/2, 240s)` 边界（**30 秒 / 半长 / 4 分钟**）逐条断言；**改标签不丢历史** |
| **V7** | **C2 恢复** | 恢复后**必须处于暂停**；**歌单身份不一致时不恢复**；**恢复成功后存档被清空** |
| **V8** | **D1 键盘契约** | ↑/↓ 小步 · PageUp/PageDown 大步 · **Home/End 到最小/最大** · 越界 `aria-invalid` |

## 9. 一句话

> **本文所有的项都在做同一件事**：
> **把"我觉得"换成"我能证明"，把"替你决定"换成"告诉你事实"。**
>
> ⭐ **而本轮最重要的一条，是踩出来的**：
> **表量的是「节目」，不是「通路」** —— 相关度、LUFS、DR、频谱，
> **在位精确和在重采样的机器上读数完全一样**。
> **所以"用表来判决保真"是个听起来很对、其实无效的想法**（我第一版就写错了一条）。
> **判决只有一条路：做减法。**
>
> **A2 让文件自己说话** —— 你那个"糊"的悬案，**最可能一步就有答案**。
> **A1 让设备自己说话** —— 零硬件依赖，精度到每一位，且**先证明尺子是直的**。
> **B1 是调音台上的表** —— 调中侧宽度时给你数字，**但它不是真相**（已写明）。
> **C 一组让 App 记得但不管着你** —— 唯一的情绪价值是**如实**。
> **D 一组是"做对了才叫专业"** —— 而且**其中一条现在就是错的**。
>
> **没有一条是为了看起来更高级。**
