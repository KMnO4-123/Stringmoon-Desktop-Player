## 0. 一句话结论

「本地 `.lrc`」升级成「本地 `.lrc`/`.ttml`/`.yrc` → AMLL 逐字（CC0）→ 网易云行级（原文+中译+罗马音）→ LRCLIB」，
逐字、翻译、注音、背景人声都能落到 §4.3 模型里；在线取词按契约 §4.4 的顺序、按 §5 的节流，
**命中即缓存、未命中也会记住**，所以「播放时自动查一次」不会退化成爬虫。

## 1. 先摆事实：这三条决定了整个设计

动手前先量了四件事，其中三件推翻了先验假设。**下面每个数字都是在本机跑出来的**。

| # | 假设 | 实测 | 影响 |
|---|---|---|---|
| 1 | 本地文件有标签，可按 艺人+曲名 搜 | 91 首里 **90 首没有任何标签**，只有 1 首有 title/artist/album | 必须从文件名反推身份，否则搜出去的是「TEST ROID - TEST HELIX」整串当歌名 |
| 2 | 或许有内嵌歌词（`source:'embedded'`） | **0 首**带歌词标签（`music-metadata` 全量扫过） | 在线取词是唯一现实路径；`embedded` 要等引擎侧读 tag + 加协议，见 §6 |
| 3 | 契约 §4.4 说网易云 `yv=-1` 给字级 `yrc` | **不成立**。`/api/song/lyric`、`/api/song/lyric/v1`、`lv/tv/rv/yv/ytv/yrv` 各种组合**都没有 `yrc`**；只有 `lrc`+`tlyric`+`romalrc` | 网易云这一档只能是**行级**；字级 `yrc` 在需要 weapi/eapi 加密的 `/lyric/new`，属平台层 |
| 4 | AMLL TTML DB 在墙内可取 | `raw.githubusercontent.com` 直连**超时**；`cdn.jsdelivr.net` 时好时坏；`gh-proxy.com` 前缀 **1.3 s / 50 KB 稳定** | 取文件必须走镜像链，且 404 与「镜像坏了」要区分开 |

第 3 条是这次最贵的一条：**契约里的格式说明与线上真实响应不一致**。
照契约写 `yrc` 解析器会得到一份「永远解析不到东西」的代码，而它看起来完全正确。
所以本轮按**真实响应**实现，并把这件事写成 CR-018 而不是偷偷把行级数据标成 `netease-yrc`。

## 2. 数据流

```text
                    ┌─ 附加歌词（用户手选 .lrc/.ttml/.yrc）
Track ─→ resolveLyrics ┼─ 同名歌词 song.lrc → song.ttml → song.yrc   ← 一律本地优先，命中就绝不联网
                    └─ 都没有 ─→ 渲染层问主进程要在线歌词

在线（主进程，串行 + 节流）：
  ① 曲目身份：有标签用标签；没有就按第一个「空格-空格」切「艺人 / 曲名」
  ② 网易云搜索（1 次）→ 候选逐条计分 → 分数 < 0.5 直接判「不是这首歌」
  ③ 命中则取 AMLL TTML（逐字+翻译+注音），文件不存在(404)就换下一档
  ④ 仍没有则取网易云行级（原文 + 中译 + 罗马音）
  ⑤ 都没有则 LRCLIB（只收**带时间轴**的记录）
  ⑥ 每一份候选还要过**时间轴自洽校验**（见 2.2），对不上就当作没找到、继续往下走
```

### 2.1 为什么「计分」是重点而不是装饰

找错歌词比找不到更糟：用户不会发现那是别人的版本，只会觉得播放器疯了。所以每个候选都要过：

| 证据 | 权重 | 说明 |
|---|---|---|
| 歌名归一化后**完全相等** / 部分包含 | +0.55 / +0.35 | 归一化 = NFKC + 去括号内容 + 去标点空白 + 小写 |
| 艺人 token 有交集 / 部分包含 | +0.30 / +0.15 | token 按 `, 、 & / feat.` 拆 |
| 时长差 ≤2 s / ≤6 s | +0.15 / +0.07 | 引擎本来就给每个文件正确的 `durationMs`，这是最便宜也最强的证据 |

低于 **0.5 直接放弃**（返回「没有」），并把风险独立标注：候选标题带 `cover/inst/remix/live/off vocal…`
而我们的没有 → `high`（`version_conflict`）；艺人完全不匹配或时长差 >8 s → `high`。

> 这条规则有真实代价：某些冷门曲会因为分数不够而没有歌词。这是**故意选的**——
> 没有歌词是可解释的状态，错歌词不是。

### 2.2 时间轴自洽：计分不看的那份证据

元数据（歌名/艺人/时长）都是**字符串**；而歌词自己的时间轴说的是**这首歌放完之前它唱完了没有**。
同名翻唱、live 版、剪辑版在被判成同一首时，元数据可能全对，时间轴却对不上。

阈值是**量出来的**（8 首真实曲目）：歌词末尾比曲长短 1–42 s（片尾器乐），首行在第一句前 0–27 s 出现。

| 情形 | 判定 | 为什么 |
|---|---|---|
| 歌词末尾 > 曲长 + **75 s** | **丢弃**，继续下一档 | 这不是这首的版本；留着只会对着别的歌开口型 |
| 歌词末尾 > 曲长 + 30 s | 保留，标高风险 | 可能是更长的剪辑版，也可能只是尾部多打了一句 |
| 歌词只覆盖到曲长 **45%** 以下 | 保留，标高风险 | 残词仍然唱对得上前面，不该因为不完整就丢掉 |
| 曲目 < 60 s / 没有时长 / 空歌词 | 不判断 | 提示音的「比例」没有意义 |

## 3. 逐字 / 注音 / 翻译是怎么落进 §4.3 的

| TTML/来源里的东西 | 落点 |
|---|---|
| `<span begin end>`（逐字音节） | `line.words[]` |
| `<span ttm:role="x-translation" xml:lang>` | `line.translation`（多语言时优先 `zh*`） |
| `<span ttm:role="x-roman">` | `line.romanization` |
| `<iTunesMetadata><translations|transliterations><text for="L1">` | 行内缺失时按 `itunes:key` 回填 |
| `<span ttm:role="x-bg">`（背景人声） | **并进同一行**的 `words`（AMLL 的渲染就是主句后跟 `(信じてる)`）；整行都是背景时才置 `line.background` |
| `<span tts:ruby="container">`（振假名） | **`word.ruby`**（新字段，CR-018） |
| 网易云 `tlyric` / `romalrc` | 与 `lrc` 按**时间戳**配对（±400 ms），不按行号 |

注音为什么必须是新字段、而不是塞进 `text`：逐字填充的实现是
`background-clip:text` + 透明字色，把注音放进 `text` 会连**行的文本不变式**一起破坏
（`words` 拼起来不再等于 `text`），渲染宽度与时间对齐全部跟着歪。

渲染层同理：`.lyric-ruby` 是 `.lyric-word` 的**兄弟**节点而不是子节点 —— 放进子节点会被同一条渐变裁成透明。

## 3.5 行级歌词的填充插值（同日晚追加，owner 已定）

**问题**：14 首实测里拿到歌词的 12 首，**11 首是行级**（网易云/LRCLIB 只给每行一个时间点）。
行级数据没有字级时间，逐字填充就完全不亮 —— 而这个播放器的歌词体验主要靠那条逐渐亮起的填充。
不做插值，这个曲库里绝大多数歌永远是「整行变色」。

**契约依据**：§4.3 原文允许「按字/词等分线性插值」，但要求 `wordByWord` **必须为 false**。
所以插值是**渲染视图**里的一步，模型一个字节都不改：

```
缓存 / IPC / Lyrics 模型          ← 保持数据源原样（wordByWord 是事实）
        ↓ applyLyricsOffset（偏移）
        ↓ withInterpolatedWords（shared/lyrics-interpolate.ts）
渲染视图（words 补齐，wordByWord 不变）
```

这样做的好处很实在：插值算法改了就改了，**不用清缓存、不用重新联网**；
而且「这一行是插出来的」可以直接从「有 words 但 wordByWord=false」推出来，**不需要新增字段**。

| 决定 | 取值 | 理由 |
|---|---|---|
| 切分单位 | CJK 按**字素簇**（`Intl.Segmenter` grapheme），拉丁按**词** | 按码点切会把拗音（きゃ）、emoji、组合音标在字形中间断开（M3 方案 §5.2 已为逐字填充定过这条） |
| 时间分配 | 按**可演唱字符数**加权，不是等分 | 「無敵の笑顔で」和「あ」不该分一样长；空白与标点不被唱，所以不占时间 |
| 太短的行 | 时间窗 < 200 ms 不插值 | 200 ms 分不出可读进度，只会闪 |
| 已有字级的行 | 原样返回（对象身份都不变） | 数据源的真实时间绝不被覆盖 |
| 标注 | 标题「同步歌词 · **插值**」+ 底栏「行级·插值」 | 契约要求如实标注；原生逐字仍标「逐字歌词」 |

**真实 DOM 验证**（electron，非单测）：多字行级行「行级歌词也能填充」→ 补出 **8** 个词；
已带字级数据的行仍保持**恰好 1** 个自己的词（没被覆盖）；标题与底栏都出现「插值」字样。

## 3.7 把在线歌词存成本地文件（同日追加）

在线结果原本只存在 app 数据目录的缓存里，而缓存**跟着路径走**——文件一改名或换目录，歌词就没了。
所以加了一个显式动作：歌词栏的「保存到本地」把当前这份**在线**歌词写成**音乐旁边的同名 `.ttml`**。

| 结果 | 为什么这么做 |
|---|---|
| 本地文件成为 §4.4 第一顺位 | 存下来之后这首歌**再也不联网** |
| 跟着音频文件走 | 改名、移动、换机器都还在（缓存不行） |
| **不覆盖已有文件** | 已存在就报错停下。用户的文件比我们的自动化重要 |
| 保存的是**缓存里的源歌词**，不是界面上的插值视图 | 把插值出来的词级时间写进文件，就是把「猜的」永久固化成「测的」 |
| 保留在线缓存 | 用户把文件删了，下一次解析还能立刻退回缓存那份 |

**为什么是 TTML 而不是 LRC**：LRC 装不下这份数据。我们的模型每行有翻译**和**罗马音，
而 LRC 只能用「同一时间戳再来一行」表达一种附加轨——第二行是翻译，第三行就无处可放
（解析器会把同一时间戳的后续行当重复丢掉）。也就是说 **LRC 会静默丢掉罗马音**，
而那正是日文歌最需要的东西。TTML 有 `x-translation` / `x-roman` 两个独立角色，
还能保住逐字时间与注音（ruby），并且它本来就是 §4.4 的第一顺位格式。

**正确性标准只有一个：写出来的文件必须能被我们自己的解析器原样读回**（往返测试）。

真实曲目端到端（2026-10-17，`Ave Mujica - Imprisoned XII`）：

```text
在线结果: netease  24 行  翻译=true  罗马音=true
已保存: Ave Mujica - Imprisoned XII.ttml  6919 字节
<p begin="00:13.390" end="00:20.220" itunes:key="L1">ねじれた空を描いて思うの
   <span ttm:role="x-translation" xml:lang="zh-Hans">描绘扭曲天空，我不禁去遐想</span>
   <span ttm:role="x-roman" xml:lang="ja-Latn">ne ji re ta so ra wo e ga i te o mo u no</span></p>
重新解析来源: sidecar  行数=24     ← 本地优先级生效
保存后在线缓存仍在: true           ← 删了文件还能退回
清理后来源: none
```

## 3.8 字级 `yrc`：契约第 3 顺位是**真的**，但只藏在加密接口后面（同日追加）

契约 §4.4 写「网易云 `yrc`——请求时带 `yv=-1` 即返回字级」。此前实测**明文接口永远不给 yrc**：
`/api/song/lyric`、`/api/song/lyric/v1`，`lv/tv/rv/yv/ytv/yrv` 各种组合，响应里都没有这个字段。
于是我一度把它记成「契约与线上不一致」。**这个结论是错的** —— 它只对了一半：

| 端点 | yrc |
|---|---|
| `/api/song/lyric`（明文 GET） | ❌ 从来没有 |
| `/weapi/song/lyric`（**加密** POST） | ✅ 有 |

加密用的是公开的 weapi 方案（两次 AES-128-CBC + 教科书式 RSA），只用 `node:crypto` 与 `BigInt` 实现，
见 [app/src/main/netease-weapi.ts](<<仓库根>/app/src/main/netease-weapi.ts>)。

**实测覆盖率**（2026-10-17）：中文歌 **3/6 有 yrc**（TestSinger A《测试曲 A》、TestSinger B《测试曲 B》、TestSinger《测试曲 C》有；
周杰伦翻唱版、林俊杰《江南》、毛不易《消愁》没有）；**本机 91 首日文歌 8 首抽样，0 首有** ——
逐字打轴主要发生在中文歌上。所以对你的曲库，这一档暂时不产生收益，但链路是对的。

### 3.8.1 ⚠️ 真实数据抓出的解析 bug：字偏移是**绝对毫秒**

第一版按「行起点 + 字偏移」实现（契约文字里的「字起点」可以两读）。真实数据一眼就否了它：

```text
yrc: [21110,1660](21110,370,0)简(21480,340,0)单(21820,950,0)点
lrc: [00:21.056]简单点            ← 同一句
```

若按相对解释，第一个字会落到 `21110 + 21110 = 42220 ms`，比这一行自己结束（22770）还晚。
所以**字偏移就是绝对毫秒**。修正后同一行解出 `简@21110 / 单@21480 / 点@21820`，与 lrc 的 21056 对齐（差 54 ms）。

同一套格式也存在「相对行首」的产出工具，所以解析器做成**数据自证**：先按绝对解释，
若解析出的字整条落在本行区间之外、而相对解释落在区间之内，就改用相对；两种都不像就退回行级。
这条规则有正反两个测试钉住。

### 3.8.2 weapi 会被限流，所以它是 best-effort

同一套加密参数在**连续探测约 10 次之后开始返回 `200` + 空 body**，换歌换 id 都一样，隔一段时间才恢复。
这是服务端限流，不是参数算错。因此：

- 空 body 按**失败**处理（否则会误判成「这首歌没有字级歌词」）；
- 失败立刻退回明文接口（行级），宁可降级也不没有歌词；
- 连续 2 次失败 → **熔断 10 分钟**不再尝试。

用户日常的频率（一首歌一次、命中即缓存）远低于触发线。

## 3.9 人工纠正匹配：候选列表（同日追加）

计分是启发式，**错配必然会发生**。在此之前用户唯一的动作是「重新查一次」——而重查大概率还是同一个结果。

新增一个「换一个」按钮：主进程只发**一次搜索请求**把候选（标题 / 艺人 / 时长 / 计分 / 风险）列出来，
用户点了哪一条才去取哪一条的歌词。选中后缓存打 `pinned` 标记 —— 之后播这首歌直接用这个选择，
不会又退回自动计分挑的那一条。候选仍然要过时间轴自检（明显不是这首的会被拒，并在面板里说明）。

## 3.10 内嵌歌词 `source:'embedded'`（同日追加）

§4.4 第 1 顺位写的是「**内嵌**/本地歌词文件」，此前只做了「本地文件」那一半。
现在补上内嵌：**用应用侧已有的 `music-metadata` 读标签**（封面早就在用它），而不是改引擎。

- 只接受**带时间轴**的内嵌歌词（很多 Vorbis 的 `LYRICS` 值本身就是 LRC 文本）。
  没有时间轴的内嵌歌词无法驱动高亮，硬塞进来就是伪造同步，宁可不显示。
- `SYLT`（逐条 `{text, timestamp}`）先拼成 LRC 再交给统一解析器，不引入第二套时间模型。
- 优先级：手选关联 → 同名文件 → 文件内嵌标签（同一顺位内的合理顺序）。

**实测收益**：本机 91 首 FLAC **0 首**带任何歌词标签（`common.lyrics` 与原生 `LYRICS/USLT/SYLT` 全扫）。
所以这条是为通用性做的，不动引擎是刻意的：为 0 收益去改协议、重建引擎、写 CR 不划算。

## 3.11 冷启动预取：owner 裁定**不做**（2026-10-17）

唯一能抹掉 1–2 秒冷启动空窗的办法是「在播放之前先查」，也就是预取；
而契约 §5 写着「禁止任何批量/循环拉取」「不做后台自动扫描歌单」。这个矛盾交给 owner 定：

> 裁定：**不预取，保持现状**。只在开始播放这首歌时查一次，命中缓存后不再联网。

所以冷启动的 1–2 秒是**有意保留**的，不是漏掉的优化项。

### 4.1 两个被实测抓出来的缺陷（已修）

1. **占位符被当成歌词**：网易云对没有歌词的歌不返回空，而是返回 `[00:00.00]纯音乐，请欣赏`
   或 `[00:00.00]暂无歌词`。第一版直接把它渲染成一行歌词，`Hero Theme` 就会显示「纯音乐，请欣赏」。
   现在区分为两种结论：`instrumental`（确认无人声，**不再**去 LRCLIB 找——那只会找到同名的别的歌）
   与 `none`（曲库没有，允许继续兜底）。
2. **艺人名被当成多人**：LRCLIB 的 `artistName` 是整串，第一版按 `&` 拆开渲染成 `MYTH / ROID`。
   现在展示保持整串，拆词只发生在计分内部。

## 5. 契约 §5 的节流怎么落实的

| 约束 | 实现 |
|---|---|
| 同平台请求间隔 ≥1 s | 平台级令牌桶：网易云 **1200 ms**、LRCLIB 1200 ms、AMLL 镜像 300 ms（CDN，非账号） |
| 禁止批量/循环拉取 | 一次播放最多 1 次搜索 + 1 次歌词 + 1 次 AMLL；**不预取、不后台扫全库** |
| 失败退避 | 收到 `-460`/`460` 立即把该平台标记为 **blocked**，本场会话不再请求，并报给用户 |
| 间隔口径 | 按**请求发起时刻**算（不是「上一次结束之后」）：串行队列保证不并发，同时省掉一次请求的耗时（本机 ~0.6 s） |
| 凭据存放 | 本轮**不使用任何账号凭据**（全部走未登录公开接口），`safeStorage` 留给平台层 |
| 重复请求 | 命中缓存永不重查；未命中记 7 天（`lyrics-online.json`） |

### 5.1 延迟：一次实测调优（9.2 s → 2.4 s）

单曲「冷启动」耗时（缓存没有时才付）：

| 阶段 | 实测 | 说明 |
|---|---|---|
| 初版 | 1.5 – 4.2 s | 网易云搜索 + lyrics + AMLL 探测 |
| 限速口径改为「发起时刻」 | −0.6 s | 契约要的是间隔，不是「结束后再等」 |
| **发现真问题** | **最坏 9.2 s** | 图书馆里 13/14 的歌根本没有 AMLL 文件，那一档要白跑两跳；而 jsDelivr 挂住时要等满 **8 s** 超时才回来 —— 预算只在「两次尝试之间」检查，**拦不住已经在飞的请求** |
| 修法 | 整档 **2 s 预算** + 每次尝试的超时压进剩余预算 + 连续 3 次失败**熔断 10 分钟** | 超预算就放弃逐字档，直接退回网易云行级（它也有译文与罗马音） |
| 结果 | **1.3 – 2.4 s** | 同一批歌，同样的网络条件 |

这条值得单独记：**「有时间预算」和「预算真的生效」是两件事**。
第一版有 deadline 变量、也有 `if (now() > deadline) break`，看起来完全正确，
但它只能挡住下一次尝试，挡不住正在进行的那一次 —— 而慢恰恰发生在正在进行的那一次里。

## 6. 已知边界（不掩饰）

- ~~没有字级 `yrc`~~ → **已做**（见 §3.8）：weapi 加密接口能拿到，中文歌覆盖率约 3/6，本机日文库 0/8。
  没有 yrc 的歌仍退回行级，`wordByWord=false` 如实标注。
- ~~`source:'embedded'` 仍未实现~~ → **已做**（见 §3.10）：应用侧用 `music-metadata` 读，不动引擎。实测 0/91 有内嵌歌词。
- **多路复用 Ogg 与链式 Ogg 不影响歌词**，但这里一并记：歌词的匹配只认曲目身份，不认容器。
- **没有离线歌曲指纹匹配**（如 Chromaprint）：同名不同版本仍可能靠时长判断，冷门曲会没有歌词。
  现在至少有「候选列表」让用户自己纠正（见 §3.9）。
- **AMLL 镜像依赖第三方**：`gh-proxy.com` / `cdn.jsdelivr.net` 都不可控；两者都挂时该档跳过，
  不影响网易云与 LRCLIB 两档。
- **自动取词默认开启**（owner 在询问窗口选定），可在「设置 → 本地曲库」里关掉；关掉后只有工具栏的
  「在线查找」按钮会联网。
