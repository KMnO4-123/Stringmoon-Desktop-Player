## 0. 一句话结论

十个 EQ 槽位从「固定频率 + 全局 Q」升级成**完整参数带**（每段自己的频率 / Q / 峰值·低架·高架），
于是 AutoEQ 的参数预设与耳机补偿曲线可以**原样**吃进来；预设、外部导入、目标曲线、耳机库都进了音效界面。

## 1. 为什么必须动引擎（实测，不是设计偏好）

实测 AutoEQ 的耳机预设：

```text
Filter 1: ON LSC Fc 105 Hz Gain 6.5 dB Q 0.70      ← 低架滤波，旧结构里不存在
Filter 3: ON PK Fc 8445 Hz Gain 3.3 dB Q 1.61      ← 任意频率，旧结构里频率固定
Filter 9: ON PK Fc 6639 Hz Gain 2.2 dB Q 5.82      ← Q 超出旧全局上限 4
```

旧引擎是 SPEC 3.4 的十段 **31.25 Hz–16 kHz 固定频率** + **一个全局 Q**。这三条一条都写不进去。
把外部曲线「拟合到十段」只能近似（±1–3 dB）且**永远表达不出架式滤波**，所以按 owner 裁定扩展引擎。

**兼容性**：新字段全部零初始化，零值 = 「沿用 SPEC 网格频率 / 全局 Q / 峰值」。
默认 `DspParams` 产生的系数与改动前逐位相同 —— 既有黄金频响测试（±0.1 dB）一个数都没改就继续通过。

## 2. 应用侧的四条路

| 来源 | 处理 | 是否近似 |
|---|---|---|
| AutoEQ `ParametricEQ.txt`（含 LSC/HSC/任意 Q） | 直接映射到十个槽位 | **否**，原样 |
| AutoEQ `FixedBandEQ.txt`（十段 PK / Q1.41） | 直接映射（频率用文件里的取样值） | **否** |
| Equalizer APO 配置 / REW 参数导出 | 同上；`BW Oct` 按 RBJ 公式换算成 Q | **否** |
| `GraphicEQ:` / CSV 曲线（密集点） | 贪心拟合到十个参数带，**误差算出来显示** | **是** |
| 目标曲线（Harman over-ear 2018/2015/2013、in-ear 2019） | 同密集曲线 | **是** |

不支持的指令（`LP`/`HP`/`Include:`/`Channel:`）**逐条进提示**，不静默丢弃 —— 一份导入报告比一条「导入成功」有用。

### 2.1 目标曲线的数据来源与归一化

来自 AutoEQ 仓库 `targets/` 的公开 CSV（`frequency,raw` 两列，695 个频点），
按 1/6 倍频程重采样到 60 点、20 Hz–20 kHz。

⚠️ **必须归一化**：原始 CSV 是绝对响应，而均衡器要的是相对形状。
统一减去 1 kHz 处的值，让每条目标曲线在 1 kHz 为 0 dB —— 否则「套上 Harman 曲线」会连整体音量一起抬高约 4 dB。
这一点有测试钉住（`eq-targets.test.mjs`：1 kHz 处 |gain| < 0.2 dB）。

⚠️ 十段逼近目标曲线**必然有误差**（目标 10 kHz 以上滚降很陡，最低约 -15 dB，而单段增益上限 ±12 dB）。
界面在选中目标曲线时**直接显示平均拟合误差**，不假装无损。

## 3. 交互

- **图上拖点**：横拖改频率、竖拖改增益，两者同时生效。拖动与滑杆走**同一个命令队列**（80 ms 合并），
  所以不会出现「拖拽一套行为、滑杆另一套」.
- **键盘可达**：拖拽只是增强。频率 / Q / 类型 / 增益各有独立的滑杆与下拉（可 Tab 聚焦、方向键调节），
  没有哪个设置只能用鼠标到达。
- **预设分组**：内置音色 / 目标曲线 / 耳机补偿 / 已导入。
- **导入**：选文件即解析、应用、并存进「已导入」；同名视为替换，不堆重复行。
- **在线获取**：输入 AutoEQ 的**精确型号名**（仓库目录名）→ 经 gh-proxy 取回并缓存。
  取不到时的错误会说明「型号名要精确」，而不是含糊的「网络错误」。

### 3.1 为什么预设不放 localStorage

预设是**用户内容**，和歌单、元数据覆盖、无法播放记录同一类 —— 这个项目里那三样都在主进程 JSON 文档里
（原子写 + 串行化）。localStorage 只该放界面偏好：它跟着渲染进程的存储配额走，清缓存就没了。

## 5. 已知边界（不掩饰）

- **没有 FIR / 房间卷积**。ECHO NEST 有「FIR / Room correction（IR 卷积）」，我们只有参数均衡。
  真正要做得给引擎加分区卷积（RT 安全、IR 文件加载、新命令 + 新 CR），是独立的一轮，
  不是「再补一个预设」。**REW 的参数导出已经能吃**（同 APO 格式，有测试），
  所以房间校正的「参数」这一半是通的，缺的是「冲激响应」那一半。
- **没有 A/B 对比与撤销**（ECHO NEST 有）。命令队列已经能承载，但需要一层快照栈，未做。
- **耳机库只有 6 款内置**。其余靠「在线按精确型号名获取」或导入文件 —— 没有型号模糊搜索索引。
- **目标曲线只有 Harman 四条**：AutoEQ 仓库 `targets/` 下能核实到的就这些（Diffuse field / BK room curve 在该目录下取不到，没有编造）。

## 6. FIR / 房间卷积（CR-020，已实现）

### 6.1.1 细节：让卷积变成「可用」而不是「存在」

**已实现。** `engine/src/convolver.{hpp,cpp}` 是均匀分区 overlap-add 卷积器；`set_ir` 命令载入 WAV，
`state.dsp.ir` 回报抽头数/声道/采样率/分区/延迟；界面上是音效页的「房间校正」一节。

### 6.2 已落地：把「素材这一半」问清楚了

`engine/src/probe_ir.cpp`（`--probe-ir <file.wav...>`）走**播放同一条 `MediaReader` 路径**读 WAV，报告
格式、帧数、峰值/有效值/直流、能量起止、按 1024 帧均匀分块需要多少分区，并给出能否被卷积器吃下的结论。

本机实测（两个合成素材，可复跑）：

```text
_ir-impulse.wav   pcm 16-bit 48000 Hz 1ch  4800 帧 (100 ms)
                  5 分区 × 1024，verdict: loadable
_ir-room.wav      pcm 16-bit 48000 Hz 1ch  72000 帧 (1500 ms)
                  前导 12.0 ms，71 分区 × 1024，~3328 次复 FFT/秒，verdict: loadable
```

这条探针的价值在于：**决定卷积可行性的是素材而不是算法**。一份 1.5 秒的 48 kHz 房间冲激响应就是
72000 个抽头；它决定了分块大小、每块要做几次 FFT、以及 RT 线程能不能扛住。这些数字现在是实测的，不是估的。

### 6.3 实现时做的三个决定（都写进 CR-020 了）

| 决定 | 为什么 |
|---|---|
| **IR 不走 seqlock** | 参数快照是标量；IR 是几 MB 的频域数组。用独立原子指针交接，渲染线程只在块边界换指针，控制线程保留所有权，**RT 线程从不 delete** |
| **全湿，没有 dry/wet** | 校正冲激响应本身包含直达声；混回干声就是梳状滤波。也正因为如此，IR 生效时必须**强制**走湿路径，否则会当成旁路静默输出未校正信号 |
| **固定 1024 帧延迟并如实上报** | 21.3 ms @48 kHz。分块是精度/CPU 的折中；延迟写进 `latencyFrames`，界面直接显示，不藏 |

采样率不一致时做线性重采样（不是零阶保持），并报告源采样率。

### 6.3.1 验收测试就是全部证据

```text
单位冲激卷积 → 输出逐样本等于冲激响应本身   (误差 < 1e-4)
任意信号     → 与离线暴力直接卷积逐样本对照 (误差 < 5e-4)
第一分区填满前无泄漏 / 上报延迟 == 分区长度
```

**做了 RED 反证**：去掉 IFFT 的 1/N，两条断言立刻失败（最大误差 1023.5 / 2444.7）。
这同时证明了 (a) 测试有牙，(b) `kiss_fftri` 不归一化——这个事实是测出来的，不是猜的。

### 6.3.2 踩到的三个坑

1. `dr_wav` 的 IMPLEMENTATION 只能有一处（`audio_source.cpp`），探针里再定义就是 LNK2005。
2. `drwav_seek_origin_*` 常量在 `DR_WAV_NO_STDIO` 下不存在，要按既有代码把 origin 直接转 int 传。
3. **协议来的路径是 UTF-8**，而 `MediaReader::open(std::string)` 按 ANSI 解释——中文目录直接「文件不存在」。
   必须过 `fromUtf8()`。很隐蔽：`--probe-ir` 走控制台 argv（ANSI）反而正常，只有 JSON 那条路才炸。

### 6.4 房间校正的另一半其实已经能用

REW / Equalizer APO 的**参数**导出（`Filter 1: ON PK Fc ...`）现在可以直接导入（有测试守着，见 §4），
所以「按测量结果做房间修正」这一半是通的；缺的只是「用冲激响应做」那一半。
