## 0. 项目定位（一句话，决定所有取舍）

> **自用 · Windows-only · 永不发布 · 91 首本地 FLAC 为主**
> **引擎是音频权威**（独立进程 + JSON Lines，音频样本绝不穿越通道）
> **项目存在的理由是"听清原音"**（独占 / bit-perfect / 透明链路）
> **设计系统是三通道编码**（C1 光 / C2 形 / C3 字，零色彩依赖）

**这三条边界决定了本方案里大部分取舍**：
凡与"听清原音"冲突的功能（环绕 / 空间音频 / 音效），
**都归入「音效链」并与 bit-perfect 严格互斥**，而不是偷偷开。

## 6. 风险与已知缺口（诚实清单）

### 6.0 ⭐⭐ 三条决定优化方向的实测事实（**来自 HANDOFF-A，2026-10-16**）

> **这三条比本方案里任何建议都重要** —— 它们决定「该往哪个方向优化」。

#### 事实 1：owner 真机听感 = 「糊、声场不够清晰、分离度不足」

**而引擎已经证明它是逐样本忠实的。** 这一轮把所有**能由软件改变的变量**逐个量掉了：

| 变量 | 结论 |
|---|---|
| 解码 | **逐位正确**（`--probe-decode` 91 文件 / **9.34 亿帧** / **0 分歧**） |
| 音源 | **真无损**（`--probe-spectrum` 91 首能量全部顶到自身 Nyquist） |
| DSP 链（立体声 + 出厂默认） | **逐样本恒等** |
| WASAPI 格式 | 声道掩码 / PCM / validBits / blockAlign 全对 |
| 独占 vs 共享 | **独占更好**（owner 判定） |
| 数字电平 100/50/25% | 无明确胜负 |
| 喂 DAC 的采样率 44.1 vs 96 | **无差别** |

**→ 引擎的输出缓冲之后，没有任何一个软件变量能解释它。**

⭐ **而 owner 同时说「别的播放器明显更好」。逻辑上只有两种可能**：

| 可能 | 含义 | 应对 |
|---|---|---|
| **A. 别的播放器加了东西** | 它**不忠实** —— 那不是"更好"，是"不同" | ⭐ **把染色做成用户可控、明示的一层** |
| **B. 存在尚未测量的因素** | 例如 DAC 侧 buffer 行为、驱动路径、时钟 | **用 null test 判决**（见 §10 新增的可测量项） |

⭐ **这个项目已有正当出口，且 owner 已批准过**：
[`DSP-v1-effects-chain.md`](DSP-v1-effects-chain.md) 的音效链 ——
**定位就是「与 bit-perfect 严格互斥、由用户主动开启」**，
⭐ **而中侧宽度（P1）正是控制「声场和分离度」的那个旋钮。**

**→ 所以"更高保真"的正确做法不是把忠实路径改成"听起来更好"**（那是这个项目存在的理由），
**而是把 P1/P2 做出来 —— 让"染色"成为能被看见、能被关掉、能被 A/B 的东西。**

#### 事实 2：⚠️ **Gapless 卡在测试素材上**（不是卡在实现）

> 设计已定（PROGRESS §0q），但**触发条件从不成立**：
> **本库 91 首里只有 1 首有 `album` 标签** → **同专辑 + 连续音轨号的相邻对 = 0**。

**→ 要先造素材**：手写 WAV + RIFF `INFO` 块（TagLib 认）。

#### 事实 3：⭐ 元数据极稀疏 —— **这是曲库侧真正的头号问题**

> **91 首 FLAC 里只有 1 首有 `album` 标签。**

| 受影响的功能 | 为什么 |
|---|---|
| **Gapless 验证** | 同专辑相邻对 = 0 → 无法验证 |
| **专辑聚合** | 大部分曲目落到 `dir:` 兜底分支 |
| **专辑封面** | 没有 album 就没有正确归属 |
| **专辑增益** | 专辑无法聚合 → 引擎已明确拒绝 `album.ok=false` |
| **在线匹配** | 标题/艺人/专辑三要素缺一 → 匹配率崩 |

**→ 元数据补全是「一次投入、多个功能受益」的那类工作。**

⚠️ **但要定顺序**：不要**先补完元数据再写代码** ——
应该**先让代码能处理「没有元数据」的情况**（`dir:` 兜底、`unknown` 占位符），
**补全作为独立一步**。

## 8. 附：Folia 的完整贡献（第二轮深挖，含**一处我的理解错误**）

### 8.1 ⚠️ 更正：`playerCap*` **不是音质协商**

**我此前在调研中以为 `playerCap*` 是"音质能力协商会话"——错了。**

**真相**：`PlayerCap` 是本机 **`localhost:8765` 的 WebSocket 服务**，
把**外部播放器**（OBS / 网易云 / QQ / 全民K歌）的当前曲目 + 歌词 + 播放位置**镜像进 Folia** ——
让"外部放歌也能在 Folia 看歌词"。

它的核心是**时钟锚点**（`PlayerCapClock{positionSec, durationSec, anchoredAtMs, playing}`）：
**墙钟外推、暂停冻结、按 duration 夹取**。

**⭐ 而且它没有音质降级阶梯**：真档位只是一个偏好字段
（`AudioQualityPreference = 'standard'|'high'|'lossless'|'hires'`），
**直接透传给 provider**，provider 自己回答能不能给。

**→ 结论对比**：**我方 CONTRACT 的静态降级阶梯（`auto→[hires,lossless,exhigh,standard]`）比它更稳** ——
在"选了 hires 但没会员"这个真实场景下，Folia **没有自动往下试的循环**。

**但取它一个形态**：让 provider 只回答"**这一档能不能给**"，**阶梯留在上层** ——
这样 provider 层完全无状态、可单测。

### 8.2 ⭐⭐ 最高优先级的一条：`generation` 代次去重 + stale 判定

**这是我方目前完全没有、且是真实 bug 源的两件东西。**

| **3** | `getOnlineRecoveryKey(src)` 剥到 **`origin + pathname`** | 见 §7.5.3 |

> ⚠️ **第 4 条与即点即播直接相关**：我方走 b（回环 HTTP），**不引入 FFmpeg**，
> 但**若将来要为 MP4/AAC 转码**，这条就是门禁。

### 10.3 Folia 的十二项

#### A. 歌词系统（**六项**）

| # | 条目 | 价值 |
|---|---|---|
| **1** | ⭐ **逐字形用"前缀测量法"** | `offsets[i] = measure(glyphs.slice(0,i).join('')).width` —— **offsets 是前缀宽度而非相邻差**，所以**扫光可直接按 offset 定位**，不需要累加。且两级缓存上限 **4096**（超限整体清空） |
| **2** | ⭐ **`icuFolia/`：`jieba`（自带词典）+ `BudouX`（日文断行）** | ⭐ **我方大量日文歌，BudouX 直接相关**。这是"中文用 jieba、日文用 BudouX"的**分语言断行** |
