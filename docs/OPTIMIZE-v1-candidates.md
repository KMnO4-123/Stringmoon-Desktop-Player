## 1. ⭐ 头号问题：**「为什么别的播放器更好」还没判决**

**这是本清单里唯一一条"不解开就一直在猜"的问题。**

### 现状

| 变量 | 结论 |
|---|---|
| 解码 | **逐位正确**（91 文件 / **9.34 亿帧** / 0 分歧） |
| 音源 | **真无损**（91 首顶到自身 Nyquist） |
| DSP 链（立体声 + 出厂默认） | **逐样本恒等** |
| WASAPI 格式 | 声道掩码 / PCM / validBits / blockAlign 全对 |
| 独占 vs 共享 | 独占更好 |
| 数字电平 100/50/25% | 无明确胜负 |
| 喂 DAC 的采样率 44.1 vs 96 | **无差别** |

**→ 输出缓冲之后，没有任何软件变量能解释它。**

### ⭐ 建议的判决性实验：**Null Test（相减测试）**

**逻辑**：如果"别的播放器更好"，那它要么**加了东西**，要么**存在我们没测的路径**。
**两者都能用相减测试区分开。**

```
① 用 WASAPI loopback 同时录两个播放器的输出（同一首歌、同一设备、同一起点）
② 精确对齐（关键难点：启动延迟不同）
③ 相减
   ├─ 差值 ≈ 全零  → 它没加东西 → 差异在别处（时钟/DAC/驱动）
   └─ 差值有内容  → 它加了东西 → 差异可被识别与度量
```

**⚠️ 三个必须处理的难点**（不处理会得到假结论）：

| # | 难点 | 对策 |
|---|---|---|
| **1** | **采样级对齐** | 用**脉冲/短促瞬态**做起点标记，交叉相关找偏移 |
| **2** | **时钟漂移** | 两遍录音的时钟不同源 → 分段对齐，不要全局对齐 |
| **3** | ⭐ **音量差异要排除** | 否则"更响"会被当成"更好" —— **先归一化再相减** |

**→ 这条一旦做完，"别的播放器更好"就从主观变成**可量化的事实**：
要么证明它加了东西（那我们就能选择性地做同一件事），
要么证明差异不在软件层（那就不该在软件里瞎改）。

#### ⭐ 具体工具：**DeltaWave**（`pkane2001/DeltaWave`，**GPL-3.0**）

**它把上面四步都做掉了**（已核实）：

| 步骤 | DeltaWave 怎么做 |
|---|---|
| **① 录音** | 两个播放器各播同一文件，**WASAPI loopback 各录一遍** |
| **② 对齐** | ⭐ **自动互相关求整数采样偏移** —— 解决"启动延迟不同"这个最大难点 |
| **③ 规避漂移** | ⭐ **只取非静音段，并在段内比较** |
| **④ 区分音量与波形** | ⭐ **分别报告「增益归一化前」与「归一化后」两组残差** |

⭐ **第 ④ 条是关键**：只报一个残差数字，**无法区分"它只是更响"与"它真的改了波形"**。
两个都报，**"更响"就骗不了人**。

**⚠️ 一个本地前置（与 G1 同性质）**：DeltaWave 是 **Windows 桌面应用**，
且需要先能 **WASAPI loopback 录音**。
**→ 开工前先确认这台机器能录回环** —— 不能录的话，整条路要先换方法。

### 若结论是"它加了东西"

**那正是本项目已有的正当出口** —— [`DSP-v1-effects-chain.md`](DSP-v1-effects-chain.md) 的音效链：

| 已知会被"加"的东西 | 我方怎么表达 |
|---|---|
| ⭐ **上采样 / 超采样** | 做成**显式开关**（不是偷偷做） |
| ⭐ **最小相位 vs 线性相位滤波** | 这是**pre-ringing vs post-ringing** 的真实取舍 —— **可听性需要盲测** |
| **不同的 dither / 噪声整形** | 见 §2.1 |
| **音量处理位置**（数字 vs 模拟域） | 我方目前是数字域 |
| **DAC 侧 buffer 大小** | 已排除（数字电平无胜负） |

⭐ **核心纪律**：**这些都必须做成一"层"——能被看见、能被关掉、能被 A/B**，
而不是把忠实路径改成"听起来更好"（**那是这个项目存在的理由**）。

## 2. 更高保真（**只列可测量的**）

### 2.1 ⭐ 噪声整形（noise shaping）—— 现在只有 TPDF dither

**现状**：`§0d TPDF dither` 已实现（把失真换成噪声）。
**缺口**：**只有平直 TPDF，没有误差反馈噪声整形。**

**收益是可测量的**：噪声整形把量化噪声**从人耳最敏感的中频推到高频**，
在 16-bit 输出下，**可感知频段**改善约 **10–20 dB**。

✅ **许可已核正（2026-10-16）**：SoX `src/dither.c` 与 SoXR **都是 LGPL-2.1+，不是 GPL**
——比原先预期宽松。8 条曲线系数在源码里**明文可见**：

| 曲线 | 抽头 | 抑制 | 备注 |
|---|---|---|---|
| `lip44` | 5-tap | 210 cB | Lipshitz |
| `fwe44` | 9-tap | 276 cB | F-weighted |
| `shi44` | 20-tap | **333 cB** @44.1k | Shibata |
| `shh44` | 20-tap | **383 cB** | Shibata 高强度 |

**→ 误差反馈结构是公开算法，自写系数表完全可行。**

**成本**：约 100–150 行（每个量化级一步误差累积）。

### 2.1b ⭐⭐ 【已核实·新】`preventClip` 的 peak 口径 —— **真实隐患**

> **这是本轮"查 preventClip"的实际产出。** 引擎侧无缺陷，**但应用侧可能填错数**。

**引擎是中性的**：它只接受一个叫 `peak` 的数（`dsp.cpp:138`），不关心那是哪种 peak。

```cpp
// dsp.cpp:137-144 —— 用哪个 peak 由参数决定
if (params.preventClip) {
    const float peak = album ? params.rgAlbumPeak : params.rgTrackPeak;
    if (peak > 0.0f) {
        // 封顶到 -0.1 dBFS（SPEC 3.4 的余量）
        const float ceiling = -20*log10(peak) - 0.1f;
        rg = std::min(rg, ceiling);
    }
}
// app.cpp cmdSetReplayGain —— 从命令读，缺省沿用当前值
num("trackPeak", cur.rgTrackPeak), num("albumPeak", cur.rgAlbumPeak)
```

**⚠️ 隐患**：引擎**同时**算出两个值（`analysis.cpp:91-92`）：

```cpp
out.truePeakDb   = linearToDb(truePeak);
out.samplePeakDb = linearToDb(samplePeak);
```

**而 `preventClip` 只接受一个**。若应用侧传 `samplePeakDb`，
**在采样点之间有过冲的素材上防削波会算得过松** ——
**true peak 可能比 sample peak 高 1–3 dB**，而削波发生在**重建后的模拟波形**上。

| 口径 | 依据（一手已核实） |
|---|---|
| **RG2 默认** | `-18 LUFS`、album 开、**sample peak** |
| ⭐ **更正确** | **true peak**（`libebur128` 是 **MIT** 且**已含 true peak 扫描**，ITU-R BS.1770-4） |

**→ 建议**：
1. `preventClip` 传 **`truePeakDb`**；
2. ⭐ **并在 UI / `outputNotPerfectReason` 里说明用的是哪种 peak** ——
   与已有的 `truePeakBasis`（`'oversampled'` | `'sample'`）字段**同构**；
3. ⚠️ **192k 下真峰值本身退化为样本峰值**（`interp=NULL`）→ 那时两者相同，如实标注。

**成本**：改调用点（小）+ UI 标注（小）。**但它是正确性问题，不是听感问题。**

### 2.1c ⭐ 【已核实·新】SoXR 配置的两条核对（**本条已做完**）

**① 双重 dither：不成立 —— 可以关掉这个担心**

```c
#define SOXR_TPDF      0     /* Applicable only if otype is INT16. */   ← 关键限定
#define SOXR_NO_DITHER 8u    /* Disable the above. */
```

引擎用 `soxr_io_spec(SOXR_FLOAT32_I, SOXR_FLOAT32_I)`（`audio_source.cpp:511`）
→ **`otype` 不是 INT16 → SoXR 不加 dither**。**无需设 `SOXR_NO_DITHER`。**

**② ⚠️ `SOXR_HQ` = 20-bit 精度（值得实测对照）**

`soxr.c:117-122` 的公式与 `soxr.h` 的档位定义：

```c
#define SOXR_HQ   SOXR_20_BITQ   /* = 4  → precision = 4 + 4*4 = 20 bits */
#define SOXR_VHQ  SOXR_28_BITQ   /* = 6  → precision = 4 + 6*4 = 28 bits */
#define SOXR_24_BITQ  5          /* 恰好匹配 24-bit 素材 */
```

| | 值 |
|---|---|
| 引擎当前 | `SOXR_HQ` → **20-bit** |
| 素材 | **16 / 24 bit**，链路 float32 |
| 可选 | `SOXR_VHQ`（28）· **`SOXR_24_BITQ`（24，正好匹配）** |

**⚠️ 但不能就此断言"高频被砍"**：`precision` 影响 `rej = precision × 6.02 dB` 的
**阻带抑制**与 `passband_end`，**是"重建精度"，不是"输出位深"**。

**→ 必须实测**（`--probe-resample` 造对照 + Null test）。
⚠️ **且它只在重采样路径生效** —— `passthrough_` 为 true 时**完全不走 SoXR**（`audio_source.cpp:543`）。
**DAC 支持 44.1/48/96/192 而素材正是这几档 → 同率时根本不重采样。**

**③ 顺带核实**：SoXR **支持最小相位**（`phase_response`：**0=minimum / 50=linear(默认) / 100=maximum**；
flags 有 `SOXR_MINIMUM_PHASE 0x30`、`SOXR_INTERMEDIATE_PHASE 0x10`、`SOXR_STEEP_FILTER 0x40`）
→ ⭐ **可直接 A/B 最小相位 vs 线性相位，正面回答 pre-ringing 问题**。

### 2.2 ⭐ 整数直通路径 —— **但先想清楚有没有意义**

**已知实测**：**全部 2²⁴ 个 24-bit 整数经 int→float32→int 往返逐一精确相等**。

**→ 所以"float 往返丢精度"这个理由**不成立**。

**但整数直通在一种情况下有意义**：**多级处理累积误差**。
- 单级：无收益
- **多级串联（EQ → 增益 → 声道工具 → 限幅）**：每级 float 运算都有舍入

**→ 判据**：**先测"多级串联后的往返误差"**。
若仍逐样本相等 → **不做**（复杂度不值）；
若有偏差 → 值得做，且**这条能进 C2 通道**（"链路是否真的没动样本"）。

## 3. 更人性化 / 更专业度

### 3.1 ⭐ 最该做的一条：**元数据补全**（它一次投入、多个功能受益）

**现状：91 首 FLAC 只有 1 首有 `album` 标签。**

| 受影响 | 为什么 |
|---|---|
| **Gapless 验证** | 同专辑相邻对 = 0 → **无法验证** |
| **专辑聚合** | 大部分落 `dir:` 兜底 |
| **专辑封面** | 没有 album 就没有正确归属 |
| **专辑增益** | 无法聚合 |
| **在线匹配** | 三要素缺一 → 匹配率崩 |

**→ 这是"一次投入、多个功能受益"的那类工作。**

#### ⭐⭐ 具体怎么做：Picard + AcoustID（**已核实，成本几乎为零**）

| 项 | 值（一手来源已核实） |
|---|---|
| **机制** | `fpcalc` **本地算声纹指纹**（离线）→ AcoustID 查询 → 三种结局（无 AcoustID / 有但未连 MusicBrainz recording / 有且已连） |
| ⭐ **91 首要多久** | **指纹本地算；91 次 lookup ÷ 3 req/s ≈ 31 秒**。**写标签纯本地。** |
| **批量** | 无元数据时按 **≤200 文件一批**；Picard 按 AcoustID **自动聚类**；一次提交最多 200–250 个指纹 |
| ⚠️ **限流** | AcoustID **3 req/s**；MusicBrainz **按源 IP 1 req/s**，超速是 **100% 拒绝（503）** 而非部分拒绝 |
| **许可** | `chromaprint` 自身 MIT，**但含 FFmpeg 部分 → 整体按 LGPL-2.1**；`pyacoustid` **MIT**；`fpcalc` 依赖 `libavcodec` |

⭐ **这是整份清单里性价比最高的一项**：**约 31 秒的查询**换来
Gapless 可验证 + 专辑聚合 + 封面 + album gain + 在线匹配 **五个功能同时受益**。

#### ⚠️ 补全失败时的诚实 fallback（**不要假装它是专辑**）

| 情况 | 做法 |
|---|---|
| `albumartist` 为空 | 用 `artist` |
| 同 album 下 artist 不一致 | ⭐ **回退到用目录名做聚合键，并在 UI 明标「按文件夹聚合」** |
| 合辑（Various Artists） | ⭐ MusicBrainz 规范（已核实）：VA 合辑**一律 credit 到 `Various Artists`**（MBID `89ad4ac3-39f7-470e-963a-56509c546377`）；**封面写 "X, Y, Z and many others" 不算署名** |
| DJ mix / 有明确编译人 | 用**混音人或编译人**，不用 VA |
| 多碟 | `discnumber` / `totaldiscs` |

**→ 这与 [`DESIGN-v5`](DESIGN-v5-encoding.md) 的「界面不能声称一件没发生的事」同构。**

#### ⚠️ 写标签的安全性：**TagLib 的 `save()` 不是"padding 够就原地写"**

（已核实：直接读 `taglib/flac/flacfile.cpp` 与 `toolkit/tfile.cpp` 源码）

它**重算 padding**（`MinPaddingLength = 4096`，上限 `min(1% 文件大小, 1MB)`），
然后 `insert(data, flacStart, originalLength)` —— ⭐ **整块替换元数据区，并把音频流整体平移**。

**真实事故**：**>16 MB 的 picture block 会写坏文件**（TagLib issue #1249，24 位块长度溢出，**已修**）。

**→ 比"备份 + 回滚"更安全的三条**：

| # | 做法 |
|---|---|
| **1** | ⭐ **先判"新元数据长度 ≤ 现有 VorbisComment + padding 总长"** —— 够则**只原地覆盖、不动音频流** |
| **2** | **写前记 FLAC 音频 MD5，写后校验**（foobar 的 Verifier / `foo_audiomd5` 就是这个思路） |
| **3** | 失败保留 `.bak` 并**原子替换** |

**⚠️ 但要定顺序**（重要）：
**不要先补完元数据再写代码** —— 应**先让代码能处理"没有元数据"的情况**
（`dir:` 兜底、`unknown` 占位符），**补全作为独立一步**。

### 3.2 专业度：**Roon 的 Signal Path 范式**（与我方 C2 通道天然契合）

Roon 的核心专业功能是**信号路径显示** —— 把"从文件到 DAC 每一级做了什么"画出来。

⭐ **它的一手语义（已核实，来自 Roon 官方社区）**：
**紫色 = bit perfect / Lossless**；**绿色 = DSP 介入（High quality / Enhanced）**；
⭐ **加 crossfade 立刻变 Enhanced**；⭐ **DSP 音量即使 0.0 dB 也出现在信号路径上**。

**这与我方 C2 通道（几何编码音质）是同一件事的不同表达**，
**而且我方的信息可能比它更完整**（因为我方有 `pcmPassthrough` / `outputPerfect` / `sourceExact` / `containerBits` / `validBits` / `outputNotPerfectReason`）。

**→ 建议**：把 C2 通道扩展成**一条"信号路径"**：
`文件（sourceExact）→ 解码 → DSP 各级 → 容器（containerBits/validBits）→ 端点`，
**每一级都能显示"是否动了样本"**。

**这条同时满足"专业度"与"诚实性"** —— 因为每一级都是**可核对的真实字段**。

### 3.3 专业度：**电平表的多种刻度**

**现状**：CR-015 的 meter 只有 dBFS 一种口径。

**可选增加**（按价值排）：

| 刻度 | 用途 | 值不值得 |
|---|---|---|
| **dBFS**（峰值/RMS） | 已有 | ✅ |
| ⭐ **LUFS 三种口径**（momentary / short-term / integrated） | **与响度扫描呼应**，且是广播/母带标准 | ⭐ 值 |
| ⭐ **相关度表（correlation meter）** | **直接对应"声场/分离度"** —— 正是 owner 报告的那个问题 | ⭐ **最值** |
| **VU / PPM / K-14 / K-20** | 专业但偏广播 | 低 |

⭐ **相关度表值得单独说**：owner 说"声场不够清晰、分离度不足"，
**而相关度正是"立体声宽度/相位关系"的可测量表达** ——
**它能让你在调中侧宽度（DSP P1）时看到数值，而不是只靠耳朵。**

### 3.7 ⚠️ 【已核实】「Hi-Res」这个词**不要用**

| 项 | 一手原文（jas-audio.or.jp） |
|---|---|
| **模拟** | 高域性能 **40 kHz 以上** |
| **数字** | **WAV/FLAC 96 kHz / 24 bit 以上** |
| 听感评价 | ⚠️ **「各社自行规定」**（= 没有标准） |
| ⭐ **商标** | 「Hi-Res AUDIO」与「Hi-Res AUDIO WIRELESS」**均为 JAS 注册商标**（注册号**第5654058号**）→ **使用需授权** |

**→ 结论**：**不该用这个词**（要授权、定义松散、听感项无标准）。
**改用「96/24 及以上」这类可验证的客观描述。**
