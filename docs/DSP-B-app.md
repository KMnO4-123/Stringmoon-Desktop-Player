## 3. ⭐ 本轮最容易做错的地方：C2 要能表达"音效生效"

### 3.1 背景：C2 是六段路径，其中一段是 DSP

DESIGN-v5 §3.2 定义的路径：

```
  [解码] ── [源率] ── [转换] ── [DSP] ── [输出] ── BP
     ●        ││        ────      ～～       ○       ━
```

**DSP 段的规则**（已定）：

| 状态 | 画法 |
|---|---|
| `dspActive === false` | **不画这一段**（不画"关闭"标记——那会给不存在的东西留位置） |
| `dspActive === true` | 画**波浪线 `～～`**，且**整条路径的 BP 段必须熄灭** |

### 3.2 ⚠️ 关键：**监测不算 DSP**

**这是本轮最容易搞错的判断**：

| 开了什么 | `dspActive` | `outputPerfect` | C2 画法 |
|---|---|---|---|
| 只开**监测** | **false** | **仍可为 true** | **不画波浪线**，BP 段**保持** |
| 开 crossfeed | true | **false** | 画 `～～`，BP 熄灭 |
| 开中侧增益 | true | **false** | 画 `～～`，BP 熄灭 |

**理由**：`dspModules` 的语义是「**有东西在改样本**」（CR-009 已裁定）。
**监测只读、不改一个样本 → 不进 `dspModules`。**

> ⚠️ **如果 C2 因为"开了频谱"就画波浪线、熄灭 BP，那是错的** ——
> 用户会以为自己失去了 bit-perfect，**而实际没有**。
> 这违反 DESIGN-v5 的核心原则：**界面不能声称一件没发生的事。**

**`encodePath` 的对应实现**（你的纯函数，`src/renderer/src/c2/encodePath.ts`）：

```ts
// 监测不在 dspModules 里，所以这条判断天然正确 —— 前提是引擎没把它放进去。
// 不要为了"看起来更丰富"而给 meter 单独加一段。
const dsp = state.dspActive === true
```

**你已有的断言**（`encodePath.test.ts`，见 REFS-B §4.3）保持不变即可，
但**建议补一条**：

```ts
// 新增：只有监测开启时，路径必须与"什么都没开"完全一致
expect(encodePath({ meterEnabled: true }).segs)
  .toEqual(encodePath({}).segs)          // 监测不改变路径
expect(encodePath({ meterEnabled: true }).bp).toBe(true)   // BP 段保持
```

### 3.3 音效链的 `dspModules` 取值（引擎会给，你只消费）

| 值 | 来自 | C3 文案建议 |
|---|---|---|
| `'eq'` | 现有 | `EQ 已开启` |

**注意**：`meter` **不在这个列表里**（§3.2）。

## 4. 三块 UI 的具体要求

### 4.1 电平监测（常驻主界面）

**消费 `ev: 'meter'`**（字段见母方案 §5.4）。四条要求：

| # | 要求 | 理由 |
|---|---|---|
| **1** | ⭐ **`truePeakBasis === 'sample'` 时必须显示区别** | **owner 裁定 5**：192k 下 libebur128 真峰值退化为样本峰值。**不能把样本峰值标成"真峰值"**——那是声称一个没做的测量。建议在真峰值旁加一个极小的标记或 tooltip |
| **2** | **mono 源时数组长度为 1**，UI **不要复制成两条** | 否则表上出现两条一模一样的通道 |
| **3** | **`gainReductionDb` 是限幅器的增益衰减** | 它在**限幅之前**采样（母方案 §2.3）——所以你能看出"限幅前是否过载"。**这正是这块表存在的意义**，值得给它一个独立的位置 |
| **4** | **峰值保持与衰减由引擎控制线程算好** | 你**不要自己再做时间逻辑**——否则两个衰减曲线会打架 |

**性能**：按现有纪律——**监测数据不要进全局 store**（`position` 的教训）。
它 30 Hz 更新，**必须走独立订阅**（像 `positionStore` 那样用 `useSyncExternalStore`）。

### 4.2 crossfeed（设置页）

**三档预设**（引擎会实现，你只需暴露）：

| # | 名称 | 参数 | 听感 |
|---|---|---|---|
| 0 | 默认 | 700 Hz / 4.5 dB | ≈30° 虚拟音箱 |
| 1 | Chu Moy | 700 Hz / 6.0 dB | 更强 |
| 2 | Jan Meier | 650 Hz / 9.5 dB | 最强 |

**两处 UX 建议**：

1. **给一句人话说明它是什么** —— 用户不知道"crossfeed"是什么。
   建议文案：`耳机专用：把左右声道互相馈送一点，减轻声音"卡在头里"的感觉。`
2. **提供"关"的明确选项**（`crossfeedEnabled = false`），且它是**默认**。
   理由：不开音效的人应保持逐样本恒等的原音（母方案 §6.1 的验收 1）。

### 4.3 中侧增益 + 宽度（设置页）

**与现有声道工具放一起**（`balance` / `mono` / `swapChannels` / `channelGainDb` 已经在 UI 里的话）。

⚠️ **一个语义上的注意**：`stereoWidth` **换了实现位置**（从声道工具提升为中侧阶段），
**但语义完全不变**（1.0=原样 / 0=mono / 2=最大展开）。
**UI 上的滑块范围与默认值不用改。**

## 6. 验收

### 6.1 可自动断言

| # | 断言 |
|---|---|
| **1** | 只开监测时，C2 路径与"什么都没开"**完全一致**（§3.2 的新断言） |
| **2** | `dspModules` 含 `'crossfeed'` 时，C2 画 `～～` 且 BP 熄灭 |
| **3** | 监测数据**不进全局 store**（可断言 store 的订阅者数量不因监测变化） |
| **4** | `truePeakBasis === 'sample'` 时 UI 有可见标记 |

### 6.2 必须人眼确认（**不自动判定，不自称通过**）

| 项 | 怎么验 |
|---|---|
| **监测常驻是否抢注意力** | 与 C2 + 歌词同时在场，确认 DESIGN-v5 §6.1「一屏一个重心」没被破坏 |
| **30 Hz 刷新的手感** | 换 60 Hz 是否更顺但更费；看是否有抖动 |
| **频谱的对数聚合是否好看** | 32 段 vs 64 段，哪个在音乐上更有分辨力 |
| **crossfeed 的文案是否让人懂** | 找一个不懂音频的人看那句话 |
