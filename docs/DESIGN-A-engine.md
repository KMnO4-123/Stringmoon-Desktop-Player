## 1. 为什么这事和你有关系

界面系统 v5 的核心装置叫 **C2（形通道）**，它是**一条六段的信号路径**：

```
  [解码] ── [源率] ── [转换] ── [DSP] ── [输出] ── BP
     ●        ││        ────      ～～       ○       ━
```

**这条路径上的每一段，都是你上报的字段画出来的。**

| 段 | 画法 | 你的字段 |
|---|---|---|
| **解码** | 实心方 = 已解码 | `state.trackId` |
| **源率** | **竖线高度**表示采样率 | `state.sourceSampleRate` |
| **转换** | **直线 = 直通 / 折线 ∧ = 重采样** | `state.resampled` |
| **DSP** | **无 = 直通 / 波浪 ～～ = 生效** | ⚠️ **见 §3，字段还不存在** |
| **输出** | **实心圆 = 独占 / 空心圆 = 共享 / 圆+括号 = 蓝牙** | `state.outputMode` + `DeviceInfo.isBluetooth` |
| **BP** | **整条连成不中断实线 = bit-perfect** | `state.bitPerfect` |

**所以：**

> **这条路径不是"界面自己画的图"，它是你的遥测的可视化。**
> **你少报一个字段，界面就会画出一条假的线。**

**这就是 §2 那条硬要求的来源。**

## 2. ⭐ 诚实性要求（这是设计系统的前提，不是建议）

设计系统里有一条被论证过的决策：

> **降级用「虚线」，不用红色。** 因为本机**长期处于降级状态**（实测：独占驱动不触发缓冲区事件），
> 红色会失去信号价值。虚线表达"路是通的，中间有东西经过"——诚实，且不制造焦虑。

**这条决策有一个隐含前提：`degradeReason` 必须被填写。**

因为界面的画法是：

```
resampled === true           → 画折线
degradeReason 存在           → 画虚线（琥珀慢闪）
两者都没有 + bitPerfect       → 画实线（宣告"全链无改动"）
```

**如果引擎静默降级了，但没设 `degradeReason`：**
- 界面看到 `resampled=false`、`degradeReason=null`、`bitPerfect=false`
- 它会画出**一条实线**（除了 BP 段不亮）
- **用户看到的是"路径干净，只是不是 bit-perfect"——而真相是"这条路径被降级了"**
- **界面在撒谎，而且是你让它撒的**

### 2.1 硬要求

> **凡是你知道的降级事实，必须在 `state.degradeReason` 里说出来。**
> **不要因为"用户看不懂"或"不重要"而不报。**

**具体到你已经有的降级路径**（从 `engine/PROGRESS.md` §0 读到的）：

| 你的降级场景 | `degradeReason` 必须说什么 |
|---|---|
| 独占静音看门狗触发（400ms 无帧渲染） | 例如 `独占流无音频回调，已回退共享` |
| 独占打开失败 → 回退共享 | 打开失败的原因（设备不支持该格式 / 被占用） |
| 蓝牙设备 → 降级共享 | 例如 `蓝牙链路，已用共享模式` |
| `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` 重建后仍失败 | 说明实际落到的缓冲 |
| 独占被其它程序占用 | `设备被其它程序独占` |
| 自适应缓冲因 xrun 上调 | 例如 `连续 3 次 xrun，缓冲已上调至 Nms` |

**判断标准**：**任何让"实际信号路径"偏离"最优路径"的事，都要进 `degradeReason`。**
**没有降级就不设这个字段**（`null`/省略 = 界面画实线，这是正确的）。

### 2.2 反向要求（同样硬）

> **不要为了"好看"而设置或省略 `degradeReason`。**

- **不许**在正常路径上设一个无意义的 `degradeReason`（会让界面画虚线，虚报问题）
- **不许**把 `bitPerfect` 报成 `true` 除非真的成立（你的 `PROGRESS` 写着判定很严格：独占 + 源采样率 + 无重采样 + 无增益，缺一不可——**这条纪律要一直保持**）

> 界面系统里那条"界面只画引擎声明支持的东西"的原则，**主语的另一半是你**：
> **引擎只报真实发生的事。**

## 3. ⚠️ 契约缺口：DSP 段（M2 才做，但要知道）

C2 的第四段是 **DSP**：

| 状态 | 画法 |
|---|---|
| 无 DSP | **不画这一段**（不画"关闭"标记——那会给不存在的东西留位置） |
| EQ / ReplayGain 生效 | 画**波浪线 `～～`**，且**整条路径的 BP 段必须熄灭** |

**问题**：现在只有 `capabilities.dsp: boolean`（能力声明），**没有"本次播放中 DSP 是否生效"的字段**。

### 3.1 需要什么

M2 加入 EQ / ReplayGain 时，`state` 事件需要新增：

```
"dspActive": true | false          // 本次播放中是否有 DSP 生效
"dspModules": ["eq", "replaygain"] // 可选：具体哪些（C3 用）
```

**理由（写给 CR）**：
- `capabilities.dsp` 表示"引擎有能力做 DSP"，**不等于"当前正在做"**
- 界面需要后者才能画波浪线；否则只能画一段永远存在的"能力"标记，**那是把能力当状态，会误导**

### 3.2 已经存在的相关要求

SPEC §3.5 里有一条（你在 M2 会实现）：

> **EQ 开启时 Audio Status 必须表达** `dspActive = true` / `bitPerfectCandidate = false` / `bitPerfectDisabledReason = eq_enabled`

**这条与 C2 的设计完全一致**——DSP 生效 → 波浪线 → BP 不成立。**所以这不是新需求，是把 SPEC 已有的要求补成协议字段。**

### 3.3 怎么走

**走 `docs/contract-requests.md` 正规流程**（CONTRACT §8 边界铁律 3）。建议编号接在已有的 CR-007 之后。
**不要自己加字段**——即使你觉得合理。

## 4. ⚠️ 一个需要你定的事实：`xrun` 有两个来源

`protocol.ts` 里 xrun 出现了**两次**：

```ts
| { ev: 'xrun'; count: number; bufferMs: number }   // ① 事件（瞬时）
// 以及 state 里：
xrunCount?: number                                  // ② 字段（累计）
```

**设计系统两个都要用，但用途不同**：

| 用途 | 应该来自 | 为什么 |
|---|---|---|
| **C1 闪 2 次**（瞬时告警） | **① `ev: 'xrun'`** | 闪光是"刚刚发生了一件事"，事件语义正确 |
| **C2 路径上的抖动标记** | **① 事件**（触发后保留一段时间） | 同上 |
| **C3 文字 `xrun N`** | **② `state.xrunCount`** | 它是累计值，适合读数字 |

### 4.1 需要你回答的问题

**`xrunCount` 的生命周期是什么？** 请确认并在契约里写明：

| 可能的语义 | 界面后果 |
|---|---|
| **会话累计**（引擎启动至今） | C3 显示"本次运行共 N 次"——合理 |
| **每曲重置** | C3 显示"本曲 N 次"——也合理 |
| **缓冲自适应后重置** | ⚠️ 用户会看到数字突然归零，**像故障消失了一样** |

**我倾向"会话累计，不重置"**（可观测性更好，且不需要解释"为什么数字变少了"）——**但这是你的领域，你来定。**

**确定后写进 CONTRACT §3.3 或 CR 里**，因为界面依赖它。

### 4.2 顺带：两个来源要一致

如果 `ev: 'xrun'` 发了 N 次而 `state.xrunCount` 是 M，**界面会显示矛盾的数字**。
**建议**：`state.xrunCount` 是权威累计值，`ev: 'xrun'` 只做"又发生了一次"的触发信号（可以不带准确 count）。

## 6. 错误码 → 界面文案分级（需要你补的是"下一步"）

设计系统要求：**错误不能只有"失败了"**。六种错误码各有不同的下一步。

| 你的错误码 | 界面已有的分级 | **需要你确认的"下一步"** |
|---|---|---|
| `ERR_DEVICE` | 输出设备类 | 建议文案：`当前设备无法打开，已保留上一首状态` + 具体原因 |
| `ERR_DECODE` | 文件类 | `文件无法解码` + 是编码不支持还是文件损坏？ |
| `ERR_NOTFOUND` | 文件类 | `文件不存在或已被移动` |
| `ERR_STATE` | 操作冲突类 | `当前状态下不能执行该操作` + 需要先做什么？ |
| `ERR_UNSUPPORTED` | 能力缺失类 | **这条最重要**：是"引擎没实现"还是"本机硬件不支持"？ |
| `ERR_INTERNAL` | 程序类 | 提示用户上报 + 引擎日志位置 |

**`ERR_UNSUPPORTED` 需要你区分两种情况**（现在只有一个码）：

| 情况 | 用户该做什么 |
|---|---|
| **引擎没实现**（如 M1 的 `pick_folder`） | 等后续版本 |
| **本机硬件不支持**（如设备的独占格式受限） | 换设备或换格式——**这是可以行动的** |

**建议**：要么拆成两个错误码，要么在 `EngineErrorShape.message` 里明确写清是哪一种。**走 CR 流程。**

## 7. 明确**不要**做的事

| 不要 | 为什么 |
|---|---|
| **不要为了界面加字段** | 界面只画引擎**真实发生**的事。为了好看加一个"装饰性"字段，是让引擎替界面撒谎 |
| **不要自己加契约字段** | 走 `docs/contract-requests.md`（CONTRACT §8 铁律 3） |
| **不要让 `degradeReason` 承载调试信息** | 它会**直接显示给用户**（C3），要写人话，不是堆栈 |
| **不要在 C1 上做"效果"** | C1 只有 5 个操作（照搬 Nothing GDK 的真实 API），**每一次变化必须由真实事件触发**。禁止为了好看加循环动画 |
| **不要碰 `app/` 的样式** | 令牌与 CSS 全在 B 侧（`app/src/renderer/src/styles/`） |
