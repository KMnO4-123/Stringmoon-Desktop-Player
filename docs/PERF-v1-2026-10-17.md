> **状态**：现行 · **日期**：2026-10-17 · **给谁**：owner / 下一位接手者
> **上位**：[`CONTRACT.md`](../CONTRACT.md)（只读）、[`docs/INDEX.md`](INDEX.md)、[`OPTIMIZE-v1-candidates.md`](OPTIMIZE-v1-candidates.md)（音质候选，本轮不动）

## 0. 一句话结论

**播放占用与常驻占用都实质下降，功能门禁全绿。** 关键数字（同机、同协议、before/after 各 2 轮，详见 §8）：

| 用户关心的 | before | after | 变化 |
|---|---|---|---|
| 本地播放（首页，可见）渲染层 CPU | Tab 2.10–2.13% · GPU 2.64–2.85% | Tab 1.34–1.44% · GPU 1.94–2.12% | **-33% / -26%** |
| 播放中切到曲库/设置等无电平表页面 | 引擎仍 ~5%（分析照跑） | 引擎 1.95–2.73% | **分析成本归零** |

| 平台 API 服务端常驻（本机真实配置 2 源） | 173.5MB node（启动 15s、未发请求的 WorkingSet；另一口径 RSS 165.1+83.7=**248.8MB**）+ 23.6MB conhost，整场常驻 | **0MB**（按需启动、10 分钟空闲停） | **-197 ~ -272MB** |

## 1. 范围与不变量

**做**：引擎 meter 分析/序列化、JSON 数字、事件载荷；应用主进程流媒体生命周期、托盘、事件门控、preload 缺口；渲染层绘制频率/DPR/画布尺寸/重渲染面；重复结构合并。
**不做**：不改 `CONTRACT.md` / `docs/SPEC-v2.1.md`；不改引擎协议形状（唯二的载荷变化见 CR-022）；不新增 npm/CMake 依赖；不动音频默认链路（DSP 旁路、SoXR VHQ、独占/共享策略、淡入淡出都保持上一轮音频交接的最终状态）；不杀用户正在用的进程。

**不变量（改完后仍成立，均有门禁或实测）**：
- RT/feeder 路径零分配、无锁（只改了控制线程上的分析/序列化与 snapshot 的 memcpy 长度）；
- meter 事件仍是「主进程可见性 + 渲染层需求」双门控，关闭时引擎不发任何 meter 帧；
- 在线曲目 `state.trackId` 恒为空串、本地曲目 `tl_` 前缀（CR-016）仍是播放占用释放的唯一判据；
- 引擎 RSS 19.9–20.6MB（SPEC §8.2 预算 60MB），播放 30s xrun=0。

## 2. 测量方法（先看口径再看数字）

本轮所有数字都能用下面 4 个脚本重放；**每个 before/after 都声明了「无并发测量」**，否则重测：

| 脚本 | 量什么 | 怎么跑 |
|---|---|---|
| `app/.smoke/perf/measure-app.mjs` | 启动时延 / 各页面静止 CPU / 工作集+private / 隐藏 / 静音播放 / 播放中切无 meter 页面 / 引擎子进程 CPU | `cd app; node .smoke/perf/measure-app.mjs --tag=xxx --seconds=8` |
| `app/.smoke/perf/measure-engine.mjs` | 引擎按场景分相 CPU/RSS/事件字节/xrun（先 `set_muted(true)`，不出声） | `cd app; node .smoke/perf/measure-engine.mjs --tag=xxx --seconds=15` |
| `app/.smoke/perf/probe-streaming.mjs` | 带真实 `streaming.json` 的隔离 profile 启动后，平台服务端子进程数量/RSS（复测 A1） | `cd app; node .smoke/perf/probe-streaming.mjs --tag=xxx` |
| `app/.smoke/perf/probe-profile.mjs` | 播放期间渲染层主线程 CDP CPU profile（top self-time） | `cd app; node .smoke/perf/probe-profile.mjs --seconds=6` |

**口径**：CPU 是「占单核百分比」，与项目既有 `app.getAppMetrics().cpu.percentCPUUsage` 一致；引擎进程用 `TotalProcessorTime` 差值。内存同时给 working set 与 **privateBytes**（Windows working set 含共享内存，private 才接近任务管理器里「内存」）。

**噪声纪律（本轮踩过的）**：
1. **系统负载会伪造收益**：同一场景两轮可差 30–50%；before/after 必须同协议、多轮取中位，并声明无并发测量。
2. **首次播放的磁盘 I/O 会记进引擎 CPU**（实测 5.78%→3.12%），同一文件要先预热页缓存再量。
3. **旧基线里 meter on/off 差 3.23% 是噪声**：干净 A/B + 微基准三方吻合的真实增量约 +1.0–1.3%（详见 §3）。
4. **启动数字对负载敏感**：before 的两轮本身差 474ms（1400→1874ms shell）；after 两轮稳定在 1039/1085ms。机制上有 R9（扫描进度洪泛）支撑，但不要把启动改进当成本轮最大收益。
5. 会出声的工具（`test:player` / `test:listening` / `test:integration` / `soak` / `drive`）本轮一律没跑，也不该在无人时跑。
6. **量隐藏/最小化必须用会节流的壳**：`tools/player-test-app.cjs` 为 UI 测试稳定关掉了 `backgroundThrottling`，用它量隐藏 CPU 会乐观失真；本轮隐藏数据来自 `.smoke/perf/plain-app.cjs`（生产默认节流）。

## 6. 结构优化（用户点名的「优化各个结构」）

1. **两条命令队列合并**：`audio/eqCommandQueue.ts` 与 `audio/channelCommandQueue.ts` 原先各自实现了一遍「排队/合并/在途/代际/订阅发布」（约 80 行重复）。新增 `audio/patchQueue.ts` 泛型实现，两个领域模块只留「合并规则 + 参数校验」；既有 `channel-command-queue` / `frequency-commands` 测试一字未改仍全绿。
2. **引擎事件单一分发器**：原先 App 与 C1Light 各挂一个 `window.twilight.onEvent`；现在 `engineEvents.ts` 统一分发，订阅者按类型注册，避免「每加一条事件就多一个 ipcRenderer 监听」。
3. **托盘/事件职责收敛**：托盘菜单内容判据提炼成 key 比对；播放占用释放判据抽成 `playback-hold.ts` 纯函数（可单测，不再埋在 index.ts 的事件分支里）。
4. **引擎 JSON 与 IO 层只加一个可选参数**：`Io::emit(frame, reserveHint)` / `App::emitEvent(event, reserveHint)` 只增不改，命令回复走默认值，meter 帧走预分配。
5. **主进程模块按需化**：`safeStorage` 动态 import；流媒体服务端从「启动即拉起」改为「按需」本身就是最大的一处结构优化（把 249MB 的常驻第三方进程从主进程生命周期里摘出去）。

## 9. 未做 / 风险 / 后续

1. **R1 频谱刷新率上限未加**（45fps 估算 Tab -0.3~0.4、GPU -0.4~0.5%）：会改变观感，且项目此前实测 40fps 被判为卡；本轮只做等价优化。若 owner 觉得频谱可接受 45fps，再把 `SpectrumPanel`/`SpectrumGlow` 的绘制闸调低即可（代码已收敛到 `frameDraw`）。
2. **GPU 进程 private 300MB 级**：实测与 `backdrop-filter`/大面积滤镜相关（禁用后 -63MB），不是 WebGL 场景（隐藏 canvas 仅 -4MB）。这是设计语言的视觉成本，本轮只做了画布/DPR/纹理层面的安全缩减；要再降需要设计侧裁定（例如把玻璃层换成静态渐变），不在本轮擅自改。
3. **E8/E10 等引擎诊断未跑完**（SoXR 单独成本、auto 每次 open 的独占协商）：不影响本轮结论；脚本已留在 `.smoke/perf-audit/perf-engine/`。**不建议动 SoXR VHQ**（上一轮刻意的音质决策）。
