## 2. 你的任务清单（按依赖排序，**照此顺序做**）

### ✅ 门禁 G1：**已完成**（2026-10-16，PROGRESS §0v）

> **本文上一版写「不实测不能开工」。这项已经做完了，结论如下。**

| 项 | 实测结果 |
|---|---|
| **新增探针** | ⭐ **`--probe-io <file-or-http-url>`** —— 直接记录**生产** `dr_flac` 的 `read`/`seek`/`tell` |
| **实测读取模式** | 最大请求 **4096 字节**，**主要请求也是 4096**，尾部有 **3 次合法短读** |
| ⭐ **结论** | **这为 256 KiB 预读窗口提供了证据，而不是沿用猜测** |

**背景（仍是理解实现的前提）**：三个解码器的 `read_proc` 契约**一字不差**（`dr_flac.h` L428 / `dr_mp3.h` L357 / `dr_wav.h` L393）：

> A return value of **less than `bytesToRead` indicates the end of the stream**.
> Do _not_ return from this callback until either the entire bytesToRead is filled or you have reached the end.

**三条推论（已按此实现）**：

1. **`read` 不能返回部分数据** —— 那会被当成 EOS
2. **数据未就绪时必须阻塞等待**
3. ⚠️ **"网络失败"绝不能退化成"返回 0"**
   —— ⭐ **已实现并验证**（PROGRESS §0v）：
   *"网络断开探针返回非零并保留 WinHTTP 错误；**feeder 不把失败当作 EOF**，也不把部分块写入环形缓冲。"*

## 4. 验收

### 4.1 IO 后端（**最强的保证在这里**）

| # | 断言 |
|---|---|
| **1** | ⭐⭐ **`HttpReader` 与 `FileReader` 逐字节等价** —— 同一文件、两种 reader，读出的字节流**完全相同** |
| **2** | **seek 后 read 正确**：随机 seek 到 N 个位置，读出的字节与文件对应位置一致 |
| **3** | **`SEEK_END` 正确**：取"最后 64 字节"，与文件尾部一致 |
| **4** | ⭐ **不重复下载同一区间**：同一个 Range 在预读窗口内**只发一次请求** |
| **5** | **网络失败走错误路径**，不退化成 EOS |

> ⭐ **第 1 条通过 ⇒ 即点即播不可能在解码层引入任何回归。** 这是本次最重要的验收。

### 4.2 音效链

| # | 断言 |
|---|---|
| **6** | **全中性 = 逐样本恒等**（crossfeed off + 中侧 identity + 监测 on，输出**必须 bit-exact**） |
| **7** | **只开监测时 `outputPerfect` 仍为 true** |
| **8** | **crossfeed 真的降低声道间相关**（单边信号过链后，另一声道**不再为 0**） |
| **9** | **crossfeed 状态复位**（`seek` / 切歌后滤波器状态清零） |
| **10** | **纯旁路仍恒等**（`isPassthrough()` 为 true 时输出 == 输入） |

### 4.3 必须人耳确认（**不自称通过**）

| 项 | 怎么验 |
|---|---|
| **crossfeed 三档预设的听感差异** | 用**强立体声混音**（人声居中、乐器两侧），确认"头中效应"减轻 |
| **中侧增益的听感** | mid +3dB 应"人声更前"，side +3dB 应"声场更宽"——**听不出说明参数范围不对** |
| **首字节延迟** | 实测；与本地文件的 149ms 对比 |
| **seek 手感**（回环 HTTP 路径） | 跳到远端不同位置，看是否有可感的停顿 |

## 5. ⚠️ 本次实测暴露过的三类陷阱（**我方已经付过代价**）

| # | 陷阱 | 教训 |
|---|---|---|
| **1** | ⭐ **"还有没有"该由谁回答** | SPEC 9 压测的根因：**一个超报的帧数同时毒死了两套机制**。修法是「**让喂料端成为权威**」——**这与 G1 的 `read_proc` 契约是同一个形状的问题** |
| **2** | **诊断工具骗人** | 崩溃报告曾只打印 exe 基址让人自己减，**减出来是无意义的 RVA**。教训：**「一个会悄悄指错方向的诊断比不诊断更糟」** |
| **3** | **不打印关键中间量会把一个根因的两个症状追成两个 bug** | 定位 SPEC 9 时，**两轮就把症状现场的全部输入打进日志**就锁定了 |

### 5.1 ⭐ 第 4 条：**外部采样 vs 自报——"采样盲区"**（Folia 的方法学）

Folia 在自己的内存文档里写了一句值得抄的话：

> **"代码注释里的 530MB 是采样盲区"** —— worker 只在 **run 前 / run 后 / 闲置**时采 rss，
> **从不在 run 中采**。→ 所以以**外部每 2 秒 `app.getAppMetrics()` 采样为准**。

⭐ **这条对我方直接适用，而且印证了我方已有做法是对的**：
我方的性能数据（RSS 51.5MB 等）本来就是**外部采样**的，**不是引擎自己报的**。

**→ 纪律**：**引擎的性能宣称应该有外部采样支撑**；
引擎自己 `log` 出来的内存数字**只能当参考**（它看不到自己的峰值）。

**⚠️ 与 SPEC 9 压测的关系**：压测跑 30 分钟，**峰值可能出现在采样点之间**。
→ 若要断言"≤60MB"，**要么提高采样频率，要么在引擎内记录峰值**（不是当前值）。

**→ 这次做 IO 后端时，第一件事是让 `read`/`seek`/`tell` 可被 trace**（G1 需要它）。
